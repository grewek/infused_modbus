# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

This repository is implemented and functional, not greenfield: a Cargo workspace with `protocol`, `datafs` (renamed from `fuse-fs` 2026-09-29), `client`, and `server` crates, all building and tested. Both Modbus TCP and RTU are wired end to end for both binaries, covering transactions, FC 43 device-description discovery, coils, discrete inputs (FC 2), input registers (FC 4), and the full register data-type set (`u8`/`i8` through `f64`/`i64`, with configurable byte/word order). `tls+tcp://` (mutual TLS, fingerprint pinning, a server-side client-approval workflow) is also fully implemented — see "TLS transport security & client trust" below. The server writes directly into `holding-registers/`/`coils/`/`discrete-inputs/`/`input-registers/` (no `transactions/` staging — see "server direct-write model" below); the client still stages writes via `transactions/`+`TRANSACTION_END`. A device description can now declare **several machines** sharing one link, each dispatched by its own Modbus Unit ID and mounted under its own top-level directory (see "Multi-machine device description & FUSE layout" below) — this was a breaking change to the TOML format, landed 2026-09-28. Both binaries also support **three interchangeable data-representation layers** selected via `--data-representation-layer fuse|files|mqtt`: the original FUSE mount, real flat files on disk kept current via `inotify`/atomic `rename()` (the default), or an MQTT/Sparkplug B interface (`client` as a Sparkplug B Edge Node over its own embedded broker; `server` behind a local `ServerHandle`-backed Unix socket, `server-data.sock`) — see "Pluggable data-representation layer" and "MQTT (Sparkplug B) representation layer" below. `fuse`/`files` are now considered legacy (bugfixes only); new feature work targets `mqtt` going forward. See the repo's `README.md` for the current function-code support table and setup instructions, and `git log` for implementation history.

This document remains the architecture and design-decision record agreed on with the project owner — it captures *why* things are the way they are, not day-to-day implementation status, so treat it as authoritative for design rationale but check the actual code/tests for exact current behavior. Update it whenever a design decision is made or revised, including for features that are decided but not yet built (e.g. the TLS section below) — mark those explicitly as not-yet-implemented so they aren't mistaken for shipped behavior.

## What this project is

`infused_modbus` is a combined Modbus **client** and Modbus **server**, both of which expose the Modbus data they handle through a **FUSE filesystem** instead of (or in addition to) a conventional API. "Infused" refers to this live-updating FUSE projection of Modbus data.

- **Client**: acts as a Modbus master against a real PLC/device, continuously updates a local mirror of that device's data, and exposes it through FUSE.
- **Server**: acts as a Modbus slave that external Modbus masters (real PLCs) query/write against. Values it holds are mirrored into its own FUSE filesystem; when an external PLC writes a value, that change is reflected into FUSE so a local operator/process can see it.

Both Modbus TCP and Modbus RTU must be supported. **TCP is the first-class transport; RTU is supported but secondary** (resolved 2026-09-15) — TCP is the more common deployment today, so it gets the primary design/testing attention. RTU's framing in particular relaxes one part of the spec: frame boundaries are detected via the standard 3.5-character-time silence gap, but the stricter 1.5-character-time max-inter-byte-gap rule (a framing error if exceeded) is deliberately not enforced, since doing so reliably against a generic async runtime's scheduling would risk discarding valid frames over harmless jitter — see `protocol/src/rtu.rs`'s module doc comment. Both `client` and `server` support choosing TCP or RTU via a scheme-prefixed connection string (`tcp://<address:port>` / `rtu://<serial-path>:<baud-rate>`); everything built on top of the transport (transactions, polling, FC 43 device identification) works identically regardless of which one is chosen, since only the framing/transport layer differs between them.

### Device description (TOML)

**Note (2026-09-28): this section predates multi-machine support and describes the shape of a single machine's data — see "Multi-machine device description & FUSE layout" below for the actual top-level TOML shape (`[[machines]]`, one entry per machine, each nesting exactly the sections described here one level down, e.g. `[machines.registers]` instead of `[registers]`).** Kept as-is rather than rewritten in place, since it's still the accurate description of *what a machine's data section contains* — just no longer of the file's top level.

Each PLC/device has an associated TOML description supplied by the user (not auto-discovered). It describes the data the device offers:

- Register addresses and data types (e.g. holding register 40001, `u16`/`f32`, scaling/units)
- Human-readable names for registers (e.g. `Tank_Temperatur` instead of a raw address)
- Access rights per register (read-only vs read/write)

Connection details (IP/port for TCP, serial port/slave ID for RTU) are **not** part of this TOML file — they are supplied separately via a config file or CLI arguments when starting the client/server binary.

**Server "introduces itself" via FC 43 (resolved 2026-09-15):** rather than requiring the client to keep its own copy of the server's TOML in sync by hand, the client fetches it over the wire at startup using Modbus function code 43 (Encapsulated Interface Transport), MEI type 0x0E (Read Device Identification), Extended access. This FC was chosen specifically because its object model (arbitrary-length byte strings, keyed by ID) and its built-in More-Follows/Next-Object-Id continuation mechanism already solve "transfer a string too long for one response" for free — no custom chunking protocol needed on top of what the FC already does. Two private objects are used (the 0x80-0xFF range is reserved by the spec for vendor-specific use):
- `0x80` — presence flag, one byte (`0x01` = server has a description, `0x00`/absent = it doesn't).
- `0x81`, `0x82`, ... — the raw TOML source, split into chunks (each object's own 255-byte length limit, further capped in practice so a chunk plus response overhead still fits in one 253-byte PDU — see `server/src/device_identification.rs`).

The client always still requires a local `device-description.toml` argument as a fallback: if the server has no description, doesn't support FC 43 at all (a Modbus exception — e.g. a simpler/older device), or the fetch fails for any other reason, the client falls back to it rather than treating this as fatal. Fetching can take several round trips (one per response that didn't fit everything), so progress is printed as it happens — otherwise a user watching the client start up has no way to tell "still fetching" apart from "hung". Scope of the current implementation: only Extended access and these two object kinds are supported; the rest of what FC 43 can do (Basic/Regular/Individual access, the standard VendorName/ProductCode/etc. objects) plus exposing these text objects through the FUSE filesystem itself is intentionally deferred to a later pass.

### FUSE filesystem layout

**Note (2026-09-28): this section also predates multi-machine support.** Every directory named below now lives one level deeper, under `/<machine-name>/` — e.g. `holding-registers/` is really `/PumpA/holding-registers/` — except `client-trust/` (server-only, root-level, genuinely unaffected by multi-machine). See "Multi-machine device description & FUSE layout" below.

**Note (2026-09-29): this section describes the FUSE-specific presentation of this layout only.** A second, non-FUSE presentation layer exposing the identical directory shape as real flat files is implemented — see "Pluggable data-representation layer — FUSE vs. flat files" below, selected via `--data-representation-layer files` (now the default) vs. `fuse`. Everything below about paths/semantics is unaffected either way; only *how* the tree is served (a `fuser::Filesystem` vs. real files + `inotify`) differs per layer.

The mounted filesystem (per client or server instance) exposes at least:

- a `holding-registers` directory — current live values as readable files, named/structured per the TOML description. Named after the specific Modbus data type rather than a generic `data`, since other Modbus data types were meant to get their own sibling directories later — `coils`, `discrete-inputs`, and `input-registers` all now exist (see "read-only Modbus data types" below for the latter two).
- a `transactions` directory (client only as of "server direct-write model" below — this bullet describes the original, still-current client behavior) — the write mechanism (resolved 2026-09-15, after considering a single-file batch-write alternative — rejected because it's less filesystem-native: no `ls` to inspect what's staged, no `rm` to unstage a single value, and a comma-separated custom syntax to parse/report errors against):
  1. The user creates a file per value they want to change, named after the register's human-readable name from the TOML description, and writes the desired value as that file's **content** (e.g. `echo True > transactions/Stop_Process`) — not encoded in the filename. Staging happens on write, not on bare creation.
  2. Once all desired changes are staged, the user creates a sentinel file named `TRANSACTION_END`.
  3. Creating `TRANSACTION_END` triggers the actual batched Modbus write(s) for everything staged in the transaction.
- a `report` directory — one read-only file per register (`report/<name>`) showing the outcome of that register's most recent write attempt (resolved 2026-09-15, see "Write status reporting" below for the alternatives considered).

**`TRANSACTION_END` confirmation semantics (resolved 2026-09-15):** creating `TRANSACTION_END` clears the whole `transactions/` staging area immediately (matching a commit consuming its staging area — no partial/pending status is shown, see "Write status reporting" below), but this does **not** mean the write has happened yet. `fuse-fs` has no Modbus protocol knowledge, so it cannot itself confirm a write reached the real device — it only hands the drained transaction off (over an injected `std::sync::mpsc::Sender<HashMap<String, RegisterValue>>`) to whoever owns the receiving end. Values under `holding-registers/` must **not** change as a side effect of `TRANSACTION_END`, which is client/server-specific logic outside `fuse-fs`, wired up once those binaries integrate `protocol`:
  - **Server (superseded 2026-09-18 by "server direct-write model" below — this bullet describes the original TRANSACTION_END-triggered behavior, kept for history):** applies (and thus reflects) the write immediately — its own in-memory state *is* the authoritative data external Modbus masters read, so there's no separate device to round-trip with. The server no longer has a `transactions/` directory at all; the same "applies immediately, no round-trip" reasoning now drives direct writes to `holding-registers/`/`coils/`/`discrete-inputs/`/`input-registers/` instead.
  - **Client (narrowed 2026-09-16):** the Modbus write response confirms the write happened, but does **not** itself update `holding-registers/` — only the next `client::polling` tick does. This was originally "after the write response / next poll confirms it" (either could update the store), but that admitted a real race: the connection is only locked per-request, not across the later store-update step, so a poll response already in flight before a commit could still land *after* it and silently overwrite the freshly-confirmed value with a stale one. Keeping the poll loop as the *only* writer of `RegisterStore`/`CoilStore` on the client removes the race outright, at the cost of `holding-registers/<name>` lagging up to one poll interval behind `report/<name>` already showing `OK`. A full or targeted re-poll triggered by the commit itself was considered and rejected — both would add wire traffic and connection contention for a race a single-writer design avoids for free.

**Write status reporting / Milestone H3 (resolved 2026-09-15):** the simplest of the considered shapes was chosen, deliberately deferring the richer alternatives until a real confirmed-write consumer exists to show what they'd actually need (extraction-based programming: don't build the structure before a concrete need has shown its real shape):
- **Granularity: per register**, not per transaction. `report/<register-name>` mirrors `holding-registers/<name>` and `transactions/<name>` exactly. This also sidesteps needing any transaction-identity concept (transactions are anonymous today — draining one doesn't produce an ID) and handles partial multi-register failures for free: `report/A` and `report/B` are independent, no aggregate transaction-level status needed.
- **Content: a plain status word.** `"OK"` or `"FAILED: <reason>"` (`fuse_fs::WriteStatus`), not a structured record with timestamp/Modbus exception code. `fuse-fs` deliberately has no `protocol` dependency for wire/error types; a richer format was judged premature before any real writer of these reports exists.
- **Lifecycle: overwritten by the next attempt**, not persisted until manually `rm`'d. `report/<name>` always reflects only the most recent write attempt for that register. Bounded by construction (at most one entry per register); no cleanup mechanism needed. Also in-memory only, same as `RegisterStore`/`PendingTransaction` — doesn't survive a process restart.
- Like `holding-registers/` and `transactions/`, `report/` is only ever updated by whoever owns the receiving end of `transaction_sender` (see confirmation semantics above) — `fuse-fs` itself never writes to it.

This transactional, filesystem-native interface is the core "twist" of the project — treating Modbus reads/writes as file operations rather than requiring a dedicated client API.

## Server direct-write model, replacing server-side transactions (resolved and implemented 2026-09-18)

**This revises the server's half of "TRANSACTION_END confirmation semantics" above** — the client's half (staging, `report/`, poll-lag) is unchanged. Implemented and shipped; supersedes the server's previously-shipped `transactions/`+`TRANSACTION_END` behavior (Milestones H1–H3's server half), which has been removed.

**Why revisit an already-shipped decision:** questioning whether the transactional (`transactions/`+`TRANSACTION_END`) model actually earns its keep on the server surfaced two things on reflection: (1) the model's real justification was always the *client's* round-trip-to-a-real-device axis — stage several edits, commit, confirm asynchronously via `report/` since the write can genuinely fail against real hardware. The server has never had that axis: its own in-memory state is authoritative, a "write" is just a local `store.set()`, there is no device to fail against. It only inherited staging because `fuse-fs` built one shared mechanism for both roles, not because the server independently needed it. (2) Even on the client, staged writes were never wire-atomic — `transaction_consumer` sends one write per register sequentially, not a single bundled PDU — so "staging" was always local UX (assemble related edits, then commit in quick succession, each confirmed independently), never a hard atomicity guarantee. That weakens the case for keeping it server-side even for the "hide a coordinated multi-value change until it's fully applied" argument.

**Server model:** `holding-registers/<name>`, `coils/<name>`, `discrete-inputs/<name>`, and `input-registers/<name>` are **directly writable on the server only** (still strictly read-only on the client, unchanged) — `echo 5 > holding-registers/Setpoint` applies immediately, no staging step. A `WriteMode` enum (`Staged`/`Direct`) on `InfusedFilesystem`, set once at construction (`client` passes `Staged`, `server` passes `Direct`), gates every FUSE method that needs to behave differently: `getattr`/`lookup` report `0o644` instead of `0o444` for these files in `Direct` mode (necessary since the `default_permissions` mount option enforces this before `write` is ever called), and `write`/`release`/`setattr` accept these inodes alongside the `transactions/` staging path. A single direct write is handed off over the exact same `transaction_sender` channel as an implicit one-item transaction — `server::transaction_consumer` needed no restructuring, only two new `StagedValue` variants (`DiscreteInput`/`InputRegister`, alongside the existing `Register`/`Coil`) and matching store parameters, since it already dispatched purely by variant. `transactions/`/`TRANSACTION_END` are removed from the **server's** FUSE tree entirely (gated by a `transactions_enabled()` check mirroring the `client_trust_ino`-is-always-computed-but-conditionally-exposed precedent) — the client keeps them exactly as-is.

**Race-safety argument:** every write, staged or direct, is still applied by the one dedicated consumer thread reading from that one channel — nothing in `fuse-fs` mutates the stores directly. This is the exact same asynchronous hand-off already accepted for `TRANSACTION_END`-triggered server writes before this change, just triggered per single write instead of per drained batch, so no new race class was introduced.

**Resolved during implementation:** `report/` was **not** extended to cover `discrete-inputs/`/`input-registers/` — it stays scoped to registers/coils exactly as H3 defined it. Extending it wasn't needed for direct-write to work (a direct write's own `write()`/`release()` return code is the only failure signal for those two categories), and doing so would have been scope creep beyond what this change needed.

**Accepted consequence:** this was a breaking change to previously-shipped, tested server behavior (Milestones H1–H3's server half) — deliberate, per this project's established "explicit/simple over preserving existing behavior while nothing is deployed" stance (see the multi-machine schema and `server-options.toml` sections below for the same call made the same day).

## Read-only Modbus data types — Discrete Inputs (FC 2) & Input Registers (FC 4) (resolved and implemented 2026-09-18)

**TOML schema**, structurally identical to `[coils]`/`[registers]`:

```toml
[discrete-inputs]
base_address = 10000

[[discrete-inputs.entries]]
name = "Door_Open_Sensor"
offset = 1

[input-registers]
base_address = 30000
mem-layout = "abcd"

[[input-registers.entries]]
name = "Flow_Rate"
offset = 1
data_type = "f32"
```

Discrete inputs mirror `CoilDescription` (`name`+`offset` only, always 1 bit). Input registers mirror `RegisterDescription` minus `access` (always read-only) — still need their own `mem-layout`, since values can span multiple registers exactly like holding registers.

**Stores:** `DiscreteInputStore` (reuses `CoilValue`) and `InputRegisterStore` (reuses `RegisterValue`) — mirror `CoilStore`/`RegisterStore` exactly. Neither exposes a write method to `protocol`/wire code, since no Modbus function code ever lets a master write these; only the server's direct-write path or client polling ever populates them.

**FUSE:** two new sibling directories, `discrete-inputs/` and `input-registers/` — read-only on the client, directly writable on the server (see "server direct-write model" above) via the same `lookup`/`getattr`/`read`/`readdir`/`write`/`release`/`setattr` machinery `holding-registers/`/`coils/` use.

**Client:** populated exclusively by polling (`build_discrete_input_read_batches`/`build_input_register_read_batches`, same batching approach as `build_read_batches`/`build_coil_read_batches`) — no write path exists on the client, consistent with [[feedback-no-optimistic-writes]] and the fact that these values only ever come from a real device.

**Server:** each configured entry starts at a default (`false`/`0`) until directly written into via `discrete-inputs/<name>`/`input-registers/<name>`, exactly like `holding-registers/`/`coils/`.

## FC 0x16 (Mask Write Register) (resolved and implemented 2026-09-23)

**Protocol/server:** `MaskWriteRegisterRequest`/`Response` (request and response share the same wire shape — a successful response just echoes the request). Server applies `result = (current AND and_mask) OR (or_mask AND (NOT and_mask))` to a single register in place, under the same lock as the read that precedes it (no separate read-then-write lock acquisitions, so a concurrent write can't land in between). Same 1-register-wide scope as Write Single Register (FC6) — only `DataType::register_count() == 1` types, `AccessRight::ReadWrite` — for the same reason: the function code has no way to address more than one wire word.

**FUSE mapping — client-only.** Implementing the wire protocol alone (server answering an external master's FC16 request) gave no benefit to a user of this project's own `client`/`server`, since nothing here could ever *originate* one. Considered exposing it on the server's own direct-write model too and rejected: a local operator already has full read access to `holding-registers/<name>` and can compute+write a plain new value themselves with no read-modify-write race to protect against (everything already serializes through the one `transaction_sender` consumer thread) — masking only matters when writing to a *real remote device* that might be written by another master concurrently, which is exclusively the client's situation.

`transactions/<name>` now accepts a second content form alongside a plain value: `MASK <and_mask> <or_mask>` (case-insensitive keyword, whitespace-separated, each mask a `0x`-hex or decimal u16, e.g. `MASK 0x00F2 0x0025`). Deliberately kept to **one file per register**, not one file per mask component — the user explicitly rejected a three-file (value/and/or) scheme as needless filesystem ceremony. An explicit keyword was chosen over silently sniffing the content's shape (e.g. "two numbers = a mask"), matching this project's established "explicit over implicit" stance (see `server-options.toml` below) and avoiding ambiguity as new content forms are ever added later.

Staged as a new `StagedValue::MaskedRegister { and_mask, or_mask }` (client-only — the server's direct-write path never tries MASK-parsing on a plain `holding-registers/<name>` write, and has no `transactions/` to stage one from at all in `WriteMode::Direct`; `server::transaction_consumer` still needs a defensive match arm for exhaustiveness, since `StagedValue` is shared). `client::transaction_consumer` sends each masked write as its **own individual** FC16 request — Modbus has no "mask write multiple registers" function code, so unlike plain writes these can never be batched together. A MASK staged against a register wider than one wire word parses fine (parsing doesn't know which register it's for) but is rejected at send time with a clear `report/<name>` reason, matching how `encode_write_request` already rejects an over-wide plain write rather than silently dropping it at parse time.

## FC 0x11 (Report Server ID) (resolved and implemented 2026-09-23)

**TOML:** optional `server-id: Option<String>` field (sibling to `[registers]`/`[coils]`/etc., not nested in any of them) — a technician sets it once and isn't expected to touch it again, per the user's own framing of this feature. **Became per-machine 2026-09-28** when multi-machine landed (now a direct field on each `[[machines]]` entry, not a file-top-level one) — a deliberate consequence of FC11 answering per Unit ID, confirmed as part of the multi-machine restructuring, not an afterthought (see "Multi-machine device description & FUSE layout" below).

**Protocol/server:** `ReportServerIdRequest` (no fields — just the function code byte) / `ReportServerIdResponse` (`server_id: Vec<u8>` — raw bytes, not `String`, since the spec's own format is vendor-specific and `protocol` has no business assuming UTF-8; `run_indicator_status: bool`, always `true`/ON when the server answers at all, since there's no partially-running state in this project). `server::handler::handle_report_server_id` answers with the TOML-configured `server_id` when present, or `ILLEGAL_FUNCTION` when absent — deliberately the same exception as a function code never implemented at all, rather than a response with an empty id, since answering with nothing meaningful isn't really "supporting" the function code.

**FUSE mapping — client-only, deliberately not exposed on the server at all.** Same underlying reasoning as FC 0x16's client-only scoping (see above), but resolved even more narrowly here after explicit user pushback: the server's own `server_id` is config the technician already wrote into `device-description.toml` themselves and isn't expected to change — mirroring it back into the server's own FUSE tree would show them a fact they already know, so `server`'s `InfusedFilesystem` is always constructed with `server_id: None` regardless of what's in its own TOML. The client is the one place this has real value: it shows a `server-id` file mirroring whatever ended up in the client's own *effective* device description (local fallback or FC43-fetched from a real device) — worth seeing there since a technician running `client` didn't necessarily set that value themselves.

**Client scope — local display only, no wire round trip.** Considered and rejected: having `client` actively send its own FC11 request to the connected device (useful as a fallback identification path for legacy devices without FC43 support) — deliberately deferred as a separate, more complex feature with its own fallback-priority questions, per Extraction-Based Programming (no concrete need for it has shown up yet). What's implemented is simpler: `client`'s `server-id` file is just `Display`-formatted straight from whichever `DeviceDescription.server_id` it already parsed for every other purpose (registers, coils, ...) — no new Modbus traffic at all.

**FUSE implementation detail worth remembering:** this is the **first top-level regular file** in this project's FUSE tree — every other top-level entry (`holding-registers/`, `coils/`, `transactions/`, `report/`, `client-trust/`) is a directory. `InfusedFilesystem` gained a `server_id_ino` (always computed, same "always allocate, conditionally expose" precedent as `client_trust_ino`) and wired it into `lookup`/`getattr`/`read`/`readdir` at the root level only, using `FileType::RegularFile` instead of `directory_attr`. Read-only (`0o444`) unconditionally — no write path, since the value is static for the process's whole lifetime.

## FC 0x17 (Read/Write Multiple Registers) (resolved and implemented 2026-09-23)

**Server-only, no FUSE mapping — decided before implementation, not discovered after like FC 0x16/0x11 were.** FC17 combines a write and a read into one request/response round trip (write applied first). Unlike FC16's mask semantics, FC17's *operation* is nothing `client` can't already do with what exists: stage+commit a write via `transactions/`+`TRANSACTION_END` (confirmed via `report/<name>`), and read via `holding-registers/` (updated by polling, per the established single-writer design — see "TRANSACTION_END confirmation semantics"). Reusing FC17 to shortcut that into one wire round trip was considered and rejected: it would need to update `holding-registers/` from a write response's own echoed read value, which is exactly the race H2 already rejected (a poll response in flight before a commit landing after it and overwriting a freshly-confirmed value). So `client` never sends FC17 — it's purely a "serve external masters correctly" feature, like most of the function-code table.

**Protocol/server:** `ReadWriteMultipleRegistersRequest` (`read_starting_address`/`read_quantity`/`write_starting_address`/`write_values` — no separate `write_quantity` field, same reasoning as `WriteMultipleRegistersRequest`: it's always `write_values.len()`, redundant with the wire's own byte-count) / `ReadWriteMultipleRegistersResponse` (same shape as `ReadHoldingRegistersResponse` — just the read half's values, the write half isn't echoed at all). `server::handler::handle_read_write_multiple_registers` resolves **both halves fully against the static register descriptions** (write half: same register-by-register/`ReadWrite`-only walk as `handle_write_multiple_registers`; read half: same walk as `handle_read`) *before* touching `store` at all — a problem with either half rejects the whole request with no partial write, matching the module's existing "validate before applying" invariant for the other multi-register handlers. Only once both halves are known-valid does it lock `store` once, apply the write, then read — so a request that reads back the same register it just wrote sees its own write, and no concurrent request can interleave between the write and the read.

## FC 0x14 (Read File Record) (resolved and implemented 2026-09-24)

**Real-world usage researched before designing anything**, per this file's "real design conversation before implementing" convention — FC 20/21 hadn't been discussed at all before this session, unlike every other FC above. Findings (web research, not project-specific): FC 20/21 are rare compared to FC01-04/06/16 — most devices never implement them. Where they do exist, "file"/"record" almost never means an actual filesystem file; it's a herstellerspezifischer strukturierter Datenblock, most commonly an event/fault log (e.g. Schneider MicroLogic trip units: file 0x14 = event log, 100 records × 9 registers) or historical/trend data (e.g. Siemens Sentron PAC2200: file 90 = timestamp + float measurements per record). One vendor (GesySense) uses FC20/21 for firmware transfer — the concrete case CLAUDE.md's `server-options.toml` section already anticipated as the risky scenario FC21 needs gating for. Wire format confirmed against the spec's own worked example (used verbatim as a protocol test cross-check, not just round-tripped against our own encoder): request bundles `reference_type`(fixed 6)/`file_number`/`record_number`/`record_length` sub-requests; response carries only raw per-sub-request bytes, no echo of which file/record they came from. Critically, **no part of the wire protocol says what a record's bytes mean** — that's entirely vendor-specific, confirmed by a pymodbus maintainer's own framing ("how you use the data returned is not part of pymodbus").

**Scope decision, made explicitly before implementing:** kept deliberately minimal — raw bytes only, no field-level interpretation. When the (still-design-only) custom-function-codes work happens, *that's* where a byte-blob gets decoded into named/typed fields; FC 0x14 doesn't attempt it now. This also settled the client-FUSE question (research showed FC20 is typically a *client*-side read feature in practice, unlike FC17): client shows a read-only hex dump, nothing more, explicitly "don't do anything with it yet."

**TOML schema — deliberately different shape from every other section.** `[[file-records]]`, flat top-level array of tables, **no `base_address`/`offset` resolution and no `name` field**:

```toml
[[file-records]]
file_number = 20
record_number = 5
record_length = 9
```

`file_number`/`record_number` *are* the address (the wire's own two-axis addressing has no natural "base" to offset from), and there's no human-readable name — the FUSE path itself (`file-records/<file_number>/<record_number>`) is the identifier, matching how a real device's own datasheet already names these things (e.g. "File 20 = event log"). `record_length` is in 16-bit words, matching the wire field's own unit, and is fixed per entry: a request asking for a different length than declared is rejected (`ILLEGAL_DATA_VALUE`), the same "must land on an exact boundary" discipline `handle_read` already applies to multi-register values. `protocol::device_description::FileRecordDescription` — new `DeviceDescription.file_records: Vec<FileRecordDescription>` field, no validation beyond what every other section already does (no duplicate-(file_number,record_number) check, since no other section checks for duplicates either).

**Protocol:** `ReadFileRecordRequest { sub_requests: Vec<FileRecordSubRequest> }` / `ReadFileRecordResponse { records: Vec<Vec<u8>> }` (deliberately untyped — `Vec<u8>`, not any structured type, matching the "this project never interprets record bytes" scope decision). `reference_type` (always 6 per spec) isn't modeled as a field at all — encode always writes the constant, decode validates and rejects (`DecodeError::InvalidFileRecordReferenceType`) rather than accepting/ignoring other values. Hardening matches [[feedback-harden-server-against-malicious-peers]]: `byte_count`/sub-response-length validated against the actual remaining buffer before every read, not just once upfront (`DecodeError::InvalidFileRecordByteCount`, `InvalidFileRecordSubResponseLength`).

**`FileRecordStore`** (`fuse_fs`) — keyed by `(file_number, record_number)` tuple rather than a name (mirrors every other store's shape otherwise), values are raw `Vec<u8>`. `StagedValue::FileRecord { file_number, record_number, value }` carries its identity directly in the enum variant rather than relying on the channel's string key to carry it (unlike every other `StagedValue` variant) — `FileRecordStore::set` needs both numbers, not a name, so making the consumer re-parse a synthetic string key back into numbers would've been needless indirection. The channel's own `HashMap` key is still a synthetic `"{file_number}:{record_number}"` string purely for uniqueness (channel is always a one-item map for a direct write anyway), never parsed back.

**FUSE — the first two-level-nested directory tree in this project.** `file-records/<file_number>/<record_number>`: unlike `transactions/`'s dynamically-created-at-runtime inodes, this is **statically known from the TOML at construction time**, exactly like every other data type — just with an extra grouping level inserted (`file_records_ino` → one directory inode per *unique* `file_number` in `file_records`, in first-seen order → one file inode per `FileRecordDescription` entry). `unique_file_numbers: Vec<u16>` + `file_number_to_ino: HashMap<u16, INodeNo>` (forward lookup) alongside the usual arithmetic-index `*_by_ino` reverse-lookup helpers (`file_number_by_ino`, `file_record_by_ino`) — consistent with every other data type's "forward HashMap for `lookup()`, arithmetic index for `getattr`/`read`/etc." split. `file_record_by_numbers(file_number, record_number)` does a linear scan for the compound-key forward lookup within an already-resolved `file_number` (no dedicated HashMap — small entry counts, and the compound key needs the file_number as context anyway). Content is a hex dump (`"0D FE 00 20\n"`), defaulting to `2 * record_length` zero bytes until directly written — same "declared but unset = zero" precedent as `default_register_value`. Direct-write parsing (`parse_file_record_value`) accepts space-separated or contiguous hex equally (all whitespace stripped before parsing) — no length check against the register's own declared width at the FUSE write boundary (that's enforced at the wire-response boundary instead, so a technician always sees exactly what they typed on a subsequent read, even if it doesn't match). Read-only on the client, directly writable on the server (`WriteMode::Direct`, same `direct_writable_by_ino`/`writable_data_file_mode` machinery every other data type uses) — **no `report/` coverage**, same precedent as discrete-inputs/input-registers (H3 stayed scoped to registers/coils; a direct write's own `write()`/`release()` return code is the only failure signal needed).

**Real bug caught and fixed during implementation, not just a design footnote:** `client_trust`'s dynamic `approved/` inode allocator (`set_next_ino`) previously started at `rejected_log_ino + 1` — coincidentally always equal to `server_id_ino` too, since `server_id`/`client_trust` are mutually exclusive in practice (server_id is client-only, client_trust is server-only), so the collision never manifested. File records genuinely coexist with `client_trust` on the server (both need to work there), so this latent collision would have become real once file-records' own fixed inode range landed between them. Fixed by moving `file_records_ino`'s whole allocation (and `server_id_ino`'s) *before* `client_trust.set_next_ino()` is called, using the true last-fixed-inode-plus-one.

**Server:** `handle_read_file_record` resolves **every sub-request fully against the static `file_records` descriptions before touching `file_record_store` at all** — a problem with any one sub-request (unknown file/record number, or a `record_length` mismatch) rejects the whole request with no partial response, matching `handle_read_write_multiple_registers`'s "validate before applying" invariant even though FC 0x14 never writes (a partial/wrong-shaped response would be just as misleading). Also rejects (`ILLEGAL_DATA_VALUE`) if the assembled response would exceed the spec's 253-byte PDU cap, mirroring `device_identification::build_objects`'s own `MAX_PDU_LEN` discipline. Gated by `server-options.toml`'s `read_file_record` key exactly like every other FC — this session also fixed a real gap found while wiring it up: `ServerOptions::is_enabled`'s `match` was missing the `FUNCTION_CODE_READ_FILE_RECORD` arm entirely (the field existed in the struct/schema from server-options.toml's original design, since it was included "ready for when this FC exists" — but the dispatch match itself was never updated), which silently made FC20 unreachable even with `read_file_record = true`. Caught by the new handler tests themselves failing with `ILLEGAL_FUNCTION` instead of their expected exception codes — a good example of why the test coverage mattered here.

**Client:** `poll_file_records_once` — **deliberately not batched**, unlike every other `poll_*_once`: one Read File Record request per configured entry, one sub-request each. FC20 *can* bundle several sub-requests into one PDU per spec, but there's no concrete need for it yet with a rarely-used FC (per this project's extraction-based-programming convention) — revisit if it ever matters. Read-only at the time this was implemented; see "FC 0x15 (Write File Record)" below for the client-side write path that was added right after.

**Manually verified end-to-end** against real `client`+`server` binaries over real TCP (throwaway TOML + raw-socket harness, deleted after use): nested `file-records/<file_number>/<record_number>` directories appear correctly on both sides; direct-write on the server (`echo "0D FE 00 20" > file-records/4/1`, both hex forms tested) reads back correctly; a real FC20 wire request returns exactly those bytes; unknown file/record → `ILLEGAL_DATA_ADDRESS`; wrong `record_length` → `ILLEGAL_DATA_VALUE`; client's FC43-fetched device description carried the `[[file-records]]` section through correctly and its own `file-records/` mount shows the same hex dump read-only, refreshed via polling; a write attempt on the client's copy correctly fails with "Permission denied".

**FC backlog: FC 20 done.** FC 21 (Write File Record) followed immediately, same session — see below. FC 18 (Read FIFO Queue) remains hardest/last.

## FC 0x15 (Write File Record) (resolved and implemented 2026-09-24)

**Scope corrected mid-design, not assumed from the start.** Initial instinct was to mirror FC17's "server-only, client already has every equivalent tool" reasoning — wrong here, and the user caught it directly ("ist der Witz von FC21 nicht, dass wir Daten vom Client aus ändern können?"). FC17 was server-only because the client's existing `transactions/`+`holding-registers/` mechanisms already expressed everything FC17 could do faster. FC21 has no such existing client mechanism — before this change, `file-records/` was read-only everywhere on the client. Pushing data into a real device's file/record slot (the actual real-world use of FC21 — see FC20's research above) is a genuinely new capability, not a shortcut around one that already exists. Corrected plan, confirmed before implementing:

- **Client gets a real write path**, via a new `transactions/<file_number>:<record_number>` content-form (hex, reusing FC20's `parse_file_record_value`) — same "extend `transactions/`'s own content parsing, don't add a new directory" precedent `MASK <and> <or>` already established for FC16. Colon-separated naming confirmed explicitly with the user (matches the internal synthetic key already used elsewhere, see below).
- **`report/` now covers file records too** — reverses H3's original "discrete-inputs/input-registers/file-records all excluded" scope for file records specifically. That exclusion held for file records only because, at the time, the only way to populate one was the server's own direct-write (never fails, nothing to report — same as discrete-inputs/input-registers permanently). A client-initiated FC21 write has a real device round trip that can genuinely fail, exactly the case `report/` exists for.
- **Server answers real FC21 requests** by validating against the static `[[file-records]]` descriptions (same discipline as FC20's read half) and writing into the same `FileRecordStore` the direct-write FUSE path already uses — one store, three ways in now (server FUSE direct-write, server wire-FC21-from-an-external-master, and the client's own separate `FileRecordStore` after *its* FC21 send to whatever device it's polling — two distinct stores, same as every other role-specific store in this project).

**Protocol:** `WriteFileRecordSubRequest { file_number, record_number, record_data }` (no separate `record_length` field — always `record_data.len() / 2`, same "redundant with the wire's own length" reasoning as `WriteMultipleRegistersRequest`). `WriteFileRecordRequest`/`WriteFileRecordResponse` share private `encode_write_file_record`/`decode_write_file_record` helpers — per spec the response is byte-identical in shape to the request (echoes everything, data included), same "two structs, one shared codec" pattern as `WriteSingleRegisterRequest`/`Response`. Unlike `ReadFileRecordRequest`'s fixed 7-byte sub-requests, each write sub-request has its own variable length (`7 + 2*record_length`), so `decode_write_file_record` walks one sub-request at a time rather than deriving a count from `byte_count` up front — each sub-request's own `record_length` field is checked against the real remaining buffer before every read, same hardening discipline as everywhere else. 11 new PDU tests, cross-checked against the Modbus spec's own worked example bytes.

**Server:** `handle_write_file_record` validates every sub-request against the static descriptions (unknown file/record → `ILLEGAL_DATA_ADDRESS`; `record_data.len()` not matching the declared `record_length` → `ILLEGAL_DATA_VALUE`) *before* touching `file_record_store` at all — same "validate before applying, no partial writes" invariant as every other multi-item write handler. No separate PDU-size check needed (unlike the read half): the response always echoes the request exactly, so it can never be larger than the request that already arrived as one valid PDU. Learned the FC20 lesson immediately: `FUNCTION_CODE_WRITE_FILE_RECORD` was added to `ServerOptions::is_enabled`'s `match` in the same commit as the handler, not as an afterthought.

**Client:** `confirm_file_record_write` sends one FC21 sub-request per call (never batched — Modbus has no "write multiple file records" function code, same reasoning `confirm_mask_write` already established for FC16). Confirmation is stricter than the plain-write case: `interpret_write_file_record_response` doesn't just check "not an exception" (`interpret_write_response`'s shortcut) — it also compares the echoed sub-requests against what was actually sent, since FC21's response echoes the *entire* request (file/record numbers and data), not a fixed address+value pair, so a decodable-but-wrong echo (device bug, confused relay) needs to be caught rather than treated as confirmed. `client::transaction_consumer` resolves staged `StagedValue::FileRecord` entries against the known `file_records` (unknown name or wrong data length → `Failed` immediately, same pattern as registers/coils/masked-registers) and sends each individually. **Deliberately does not update the client's own `FileRecordStore` on a confirmed write** — same single-writer discipline the 2026-09-16 register/coil race fix established: only `client::polling::poll_file_records_once` ever writes that store, so `file-records/<file>/<record>` can lag up to one poll interval behind `report/<name>` showing `OK`, rather than reopening the exact race that fix was for.

**Manually verified end-to-end** against real `client`+`server` binaries over real TCP (throwaway TOML + server-options, deleted after use): staging `transactions/4:1` with hex content + `TRANSACTION_END` sent a real FC21 request, `report/4:1` showed `OK`, and the server's own `file-records/4/1` reflected the new value immediately; an unknown file record (`999:1`) was rejected at `create()` (`ENOENT`, matching the "only a real target can be staged" precedent); a wrong-length write was rejected with `report/4:1` showing `FAILED: file record 4:1: expected 4 bytes but got 1`; `file-records/` stayed read-only on the client's own mount throughout; disabling `write_file_record` via `server-options.toml` made a raw FC21 wire request come back as exception code 1 (`ILLEGAL_FUNCTION`), confirmed against the real running server.

**FC backlog: FC 20 and FC 21 both done, same session.** FC 18 (Read FIFO Queue) is the only one left, still hardest/last per the original effort ordering — no established FUSE representation for queue semantics exists yet, unlike every FC implemented so far.

## Planned: custom (vendor-specific) function codes (design resolved 2026-09-18, not yet implemented)

**Note (2026-09-28):** this design predates multi-machine support (below) and doesn't yet say whether `custom-function-codes.toml` should nest per-machine like every other data-shape config now does, or stay a single process-wide file — an open question to resolve when this is actually implemented, not assumed here.

Motivation: real devices sometimes implement genuinely non-standard function codes outside anything the Modbus spec's public FC table covers — the user's own concrete prior experience is an inverter encountered at work with entirely custom FC definitions, which he previously handled in Node-RED via `node-red-contrib-modbus`'s `flex-fc` node (a JSON-driven request/response field-map: `name`/`offset`/`type` per field, loaded from an external file). This section adapts that idea, stricter, for this project. Nothing in this section exists in code yet.

**Scope, for now: vendor-specific FC number range only** (0x41-0x48 / 65-72 and 0x64-0x6E / 100-110, per spec's own user-defined-function reservation) — reinterpreting an existing *standard* FC number (which some real devices, like the inverter, apparently do anyway) is deliberately out of scope for this first pass, revisit later if a real device actually needs it. `function_code` outside this range is a hard parse error.

**Config: new `custom-function-codes.toml`**, one file, `[[custom-function-codes]]` array-of-tables, each with `name`, `function_code`, and nested `[request]`/`[response]` field lists — consolidated into one file/one entry per FC (not separate request/response files, unlike `flex-fc`'s two separate map editors):

```toml
[[custom-function-codes]]
name = "InverterStatus"
function_code = 65

[[custom-function-codes.request.fields]]
name = "Query_Type"
data_type = "u8"
value = 1              # fixed value the client always sends for this field

[[custom-function-codes.response.fields]]
name = "Frequency"
data_type = "u16"

[[custom-function-codes.response.fields]]
name = "Status_Flags"
data_type = "u8"
```

**Stricter than `flex-fc` by design:** fields are **sequential and contiguous**, no explicit `offset` — field N+1's position is derived from field N's end, eliminating the whole class of overlapping/gapped/contradictory layouts an offset-per-field scheme like `flex-fc`'s permits. Field types reuse the existing `DataType` enum rather than inventing a narrower one. Not yet resolved: `DataType`'s multi-register byte width (e.g. `u24` occupying two padded 16-bit registers = 4 bytes) is a holding-register-framing convention that doesn't obviously apply to a raw custom-FC byte layout (a real device's `u24` field here might just be 3 raw bytes, no padding) — needs its own byte-width mapping, to be settled once this is actually implemented. Also not yet resolved: whether defining a custom FC here additionally requires enabling it via `server-options.toml`'s `[function-codes]` table for consistency with that section's explicit-opt-in stance, or whether being defined here is itself sufficient.

**Client role (master, always initiates):** builds the request PDU from the request fields' fixed `value`s, decodes the response fields into new read-only FUSE files (`custom/<name>/<field-name>`), refreshed via polling exactly like `holding-registers/` today.

**Server role (never initiates — Modbus stays strictly master-initiated, same constraint noted throughout this file):** dispatch recognizes the configured `function_code`, decodes the incoming request into read-only FUSE files under `custom/<name>/` (showing what was last asked), and the **response fields become directly writable** — reusing the exact "server direct-write model" above unchanged (an operator's write becomes an implicit one-item transaction over the same `transaction_sender` channel), so whatever was last written is what the server replies with on the next matching request. Only new state needed is a `CustomFunctionCodeStore` (keyed by field name, holding `RegisterValue`-shaped data) — no changes to the write-hand-off mechanism itself.

**FUSE layout:** a new top-level `custom/<fc-name>/` directory tree, since this data doesn't fit `holding-registers/`/`coils/`/`discrete-inputs/`/`input-registers/` at all — it isn't Modbus register/coil-addressed data, just named byte fields.

## Multi-machine device description & FUSE layout (resolved and implemented 2026-09-28)

Motivation: the user's stated direction is for a single `server` (and `client`) instance to manage several machines at once — e.g. one RTU multi-drop link or several TCP targets — from one file, rather than one process per machine. This superseded the earlier open "Multi-machine TOML schema" question: instead of a discovery-layer-only solution (an FC43-directory + FC20-per-machine idea, considered and not pursued further — see "Relationship to FC43/FC20 wire transfer" below), the schema itself natively describes multiple machines.

**Schema: `[[machines]]` array-of-tables**, one entry per machine, each carrying:
- `name` — a String identifying the machine, used directly as its FUSE top-level directory name. Must be **unique across the file** and restricted to ASCII alphanumeric characters plus `_`/`-` (no other characters, no empty string) — enforced as a parse error, not a runtime surprise, since two machines sharing a name would collide on one FUSE inode and other characters could break path handling.
- `unit_id` (`u8`) — which Modbus Unit ID on the shared link this machine answers to. This is a deliberate, explicitly-flagged exception to this file's established "TOML describes data shape, CLI/config describes connection" separation (see "Key technical decisions" below): a Unit ID is normally connection/wire-addressing information, but it's needed here to tell multiple machines described in one file apart, so it lives in the device description rather than CLI/config.
- `server-id` (optional String) — see FC 0x11's own section above; became per-machine for the same reason `unit_id` is per-machine (FC11 answers per Unit ID).
- Every other device-shape section nests one level down, structurally identical to before: `[machines.registers]`, `[machines.coils]`, `[machines.discrete-inputs]`, `[machines.input-registers]`, `[[machines.file-records]]`. Confirmed explicitly with the user before implementing that **all** these sections nest symmetrically, not just registers/coils as this section originally proposed — discrete-inputs/input-registers/file-records didn't exist yet when the original 2026-09-18 design was written, but there was no reason for them to be treated differently once they did.

```toml
[[machines]]
name = "PumpA"
unit_id = 1
server-id = "pump-a-plc"

[machines.registers]
base_address = 40000
mem-layout = "abcd"

[[machines.registers.entries]]
name = "Tank_Temperature"
offset = 1
data_type = "u16"
access = "read_only"

[machines.coils]
base_address = 0

[[machines.coils.entries]]
name = "Motor_Running"
offset = 1

[[machines]]
name = "PumpB"
unit_id = 2

[machines.coils]
base_address = 0

[[machines.coils.entries]]
name = "Motor_Running"
offset = 1
```

This was a **breaking change** to the previous single-machine TOML format (the old top-level `[registers]`/`[coils]` stopped being valid) — accepted deliberately, no backward-compatibility shim, since the project isn't deployed anywhere yet (same stance as `server-options.toml`'s default-deny and the server direct-write model above).

**FUSE layout:** each machine gets its own top-level directory named after `name`, containing the full per-machine directory set — `holding-registers/`, `coils/`, `discrete-inputs/`, `input-registers/`, `file-records/`, plus `transactions/`+`report/` **on the client only** (the server writes directly into `holding-registers/<name>`/`coils/<name>` per machine instead, per "server direct-write model" above) — e.g. `/PumpA/holding-registers/`, `/PumpB/transactions/` (client). The server's `client-trust/` subtree (TLS section below) stays exactly where it is at the filesystem root, entirely unaffected — it's about which clients may connect at all, not about any one machine.

**`fuse-fs` implementation:** the old single-machine `InfusedFilesystem` was split into a private `MachineFs` (everything per-machine — `holding-registers/`, `coils/`, etc.) wrapped by a new outer `InfusedFilesystem` (`machines: Vec<MachineFs>` + `client-trust/`'s fields, relocated unchanged) that actually `impl`s `fuser::Filesystem`. Every `MachineFs` computes its own inodes relative to a per-instance `base: u64` instead of the old fixed `ROOT_INO`/`HOLDING_REGISTERS_INO` constants, so several machines can coexist in one real inode space: `base = FIRST_MACHINE_INO + index * MACHINE_INO_STRIDE` (`FIRST_MACHINE_INO = 1<<32`, `MACHINE_INO_STRIDE = 1<<40` — astronomically larger than any realistic dynamic `transactions/` growth, so machine ranges can never collide without needing real bounds-checking). `MachineFs` no longer implements `fuser::Filesystem` directly — it keeps the same methods as plain inherent methods, since `fuser`'s `Reply*` types commit to the kernel the moment they're called, so inode rewriting has to happen *before* dispatch (via `base`), not by intercepting a reply afterward. The outer struct routes each request by resolving which `MachineFs` owns a given inode (`machine_owning_ino`) and delegating straight through, or handles root-level/`client-trust/*` cases itself. `transaction_sender`'s channel item type changed from `HashMap<String, StagedValue>` to `(String, HashMap<String, StagedValue>)`, tagged with the originating machine's `name` — one consumer thread (client or server) now services every machine's writes off one shared channel. A public `MachineConfig` struct bundles `MachineFs`'s ~16 constructor arguments (mirroring `fuse_fs::MachineStores`'s existing per-machine store bundle). Committed as `8f857e1` (protocol restructuring), `0b015aa` (`MachineStores` bundle), `7a9cca7` (this FUSE-tree split).

**Client mounting scope:** `client` mounts **all** machines described in its (possibly FC43-fetched) TOML by default — the concrete, simplest case first, per this file's own Extraction-Based Programming convention. Letting the user choose a subset remains a real desired-but-undecided follow-up (e.g. a `--machines PumpA,PumpB` CLI allowlist, all mounted if omitted) — **still not implemented**, not built alongside "mount all".

**Client wiring:** `client::polling::run_polling_loop` needed **zero changes** — it was already fully parameterized per-machine (its own `unit_id`, descriptions, stores), so multi-machine polling is just `client::main` spawning one polling task per configured machine, all sharing the one `Arc<AsyncMutex<Connection>>` (confirmed 2026-09-18, not assumed: `Connection::request(unit_id, pdu, timeout)` already took a per-call Unit ID). `client::transaction_consumer::run_transaction_consumer` became machine-aware instead: a new `MachineTransactionConfig` bundles one machine's registers/coils/file_records/report/mem_layout/unit_id, keyed by machine name in a `HashMap` the consumer resolves each received `(machine_name, transaction)` against; an unrecognized machine name is logged and dropped, not treated as fatal. **The CLI's positional `unit-id` argument is now scoped to just the initial FC 43 device-identification handshake** — each machine dispatches its own register/coil/etc. traffic afterward via its own TOML-declared `unit_id`, not the CLI one. Committed as `ded6003`.

**Server wiring — the real non-trivial half, as anticipated by the original design.** Unlike the client, `server::handler::handle_request` never received `unit_id` at all before this — decoded off the incoming ADU only to be echoed back into the response. Fixing that required a small `protocol` crate change: `protocol::tcp::serve_request`/`protocol::rtu::serve_request`'s handler closure signature changed from `AsyncFnMut(&[u8]) -> Vec<u8>` to `AsyncFnMut(u8, &[u8]) -> Option<Vec<u8>>`. **Confirmed directly with the user before implementing:** when an incoming request's `unit_id` matches no configured machine, the server now sends **no response at all** (`None`) — mirroring real RTU multi-drop bus behavior (an unaddressed slave stays silent, the master's own timeout handles it) rather than synthesizing an `ILLEGAL_FUNCTION`/gateway-diagnostic exception for a case that isn't really about the function code at all. A new `server::handler::ServerMachineState` bundles one machine's registers/stores/mem-layouts/`server_id`; `handle_request` now takes `(unit_id, pdu, server_options, machines: &HashMap<u8, ServerMachineState>, toml_source)`. Dispatch order: the `server_options` disabled-function-code gate stays unit_id-independent (a disabled FC is disabled process-wide); FC 43 answers with the whole multi-machine TOML **regardless of `unit_id` and without any machine lookup at all** — it's how a client bootstraps knowledge of every machine before it knows which unit_ids are even valid; every other function code resolves `machines.get(&unit_id)` and returns `None` if absent. `server::connection::serve_tcp_connection`/`serve_rtu_connection` collapsed from ~12 flat parameters to just the `machines` map + `toml_source` — a real simplification, not just churn. `server::transaction_consumer` became **name**-keyed (`HashMap<String, fuse_fs::MachineStores>`, matching how `fuse-fs` tags every send) — a deliberately *different* lookup key from `handler.rs`'s **unit_id**-keyed map, since FUSE addressing and wire addressing serve genuinely different purposes and must not be conflated. `server::main` builds both maps from `DeviceDescription.machines`, sourced from the same underlying `Arc`-shared stores, so the transaction consumer / wire handler / FUSE tree for a given machine always agree on the same data. One easy-to-get-wrong distinction preserved correctly: each machine's FUSE `MachineConfig.server_id` still stays `None` unconditionally (existing, already-shipped precedent unrelated to multi-machine — the server never mirrors its own configured server-id into its own FUSE tree, see FC 0x11's section above), while `ServerMachineState.server_id` carries the real per-machine value that FC11 actually answers wire requests with. TLS/admin/client-trust code paths were completely untouched by this step — none of them have any per-machine concept. Committed as `6a6e2a4`.

**`cargo build/test/clippy --workspace --all-targets` is fully clean** as of this work landing — the last remaining casualty, `fuse-fs/examples/mount_demo.rs` (broken since the initial `DeviceDescription` restructuring), was fixed same-session by wrapping its one demo machine in a `MachineConfig` named `"Demo"` (committed as `2daa919`). 645 tests pass across the workspace.

**Relationship to FC43/FC20 wire transfer:** the on-disk schema shape (one file, multiple machines) is orthogonal to how it's transferred over the wire at client startup — a single multi-machine TOML is still served as one FC43 blob (while it stays under the ~31KB ceiling), regardless of which unit_id answers (see the server dispatch section above). Splitting a large multi-machine description server-side behind an FC43-directory + FC20-per-machine fetch was considered as an alternative discovery mechanism and not pursued — FC20 is implemented now (see "FC 0x14 (Read File Record)" above), but purely for its own TOML-declared `[[file-records]]` use case; reusing it for description discovery remains a separate, undecided, low-priority idea, not automatically unlocked by FC20 existing.

## Client connection reconnect (resolved and implemented 2026-09-28)

Motivation: the user observed the real failure mode directly — killed a running `server`, watched `client` spam poll-failure log lines forever, then restarted the server and found `client` still stuck, never recovering on its own. Confirmed by reading the code: `Connection::connect_tcp`/`connect_tls`/`open_rtu` were called exactly once, at startup, in `client::main`; every subsequent I/O failure was just logged and skipped (`client::polling`) or turned into a `WriteStatus::Failed` (`client::write_confirmation`) — nothing ever redialed. This was already flagged in `client/src/main.rs`'s own doc comment ("no reconnect logic") as a known gap, not a surprise once looked into.

**Confirmed with the user before implementing:** automatic reconnect with exponential backoff (not a fixed retry interval), and retries **forever** — no giving-up-after-N-attempts cutoff. A client that outlives a server restart or a transient network blip should keep trying indefinitely rather than requiring a manual process restart once some attempt count is exhausted.

**Detection is polling-only, deliberately not wired into the write path too.** `client::polling`'s poll loop already runs continuously on a fixed interval regardless of write activity, so it's the natural, already-existing place to notice a broken connection quickly — every one of its 5 `poll_*_once` functions (registers/coils/discrete-inputs/input-registers/file-records) calls `ReconnectSignal::mark_broken()` in its existing I/O-error branch, alongside the `eprintln!` that was already there. The transaction/write path (`client::write_confirmation`/`client::transaction_consumer`) needed **no changes**: a write attempted against a still-broken connection already correctly reports `WriteStatus::Failed("write failed: <io error>")` today, and once polling's own detection heals the shared `Connection`, the very next write just succeeds again — no separate write-side detection needed, and wiring it in would've meant distinguishing a genuine I/O failure from a Modbus exception response or a decode error inside `WriteStatus::Failed`'s already-stringified reason, which isn't information that's cleanly available at that layer today.

**New `client::reconnect` module:**
- `ReconnectSignal` — `Notify` + `AtomicBool`, shared by every request-issuing task and one dedicated reconnect task. `mark_broken()` is cheap and idempotent: several simultaneous failures (e.g. every data type's poll batch failing in the same tick, which is exactly what happens — see manual verification below) collapse into a single reconnect attempt, since `Notify::notify_one()` only ever stores one pending wakeup regardless of how many times it's called before something consumes it.
- `redial()` — the per-scheme connect dispatch (`Connection::connect_tcp`/`connect_tls`/`open_rtu`), extracted out of `client::main`'s old `open_connection` so both the one-shot startup connect and every later reconnect attempt share it. Fallible (`io::Result`) rather than panicking, unlike startup connecting — a failed redial is routine and expected here, not fatal.
- `run_reconnect_loop()` — runs forever on its own spawned tokio task (one per client process, shared `Connection`/`ReconnectSignal` across every machine's polling task and the transaction consumer, exactly like `Connection` itself is shared). Waits on the signal, then redials in a loop with backoff starting at 1s, doubling, capped at 30s, until one succeeds, then swaps the fresh `Connection` into the shared `Arc<tokio::sync::Mutex<Connection>>` in place — no explicit "retry the failed request" step needed, the next poll tick or write attempt just uses the now-healthy connection naturally.

**A small, accepted, self-correcting race:** if more failures land (against the *old*, about-to-be-replaced connection) while a redial is already in flight, `mark_broken()` can set the flag again during that window; right after a successful swap, the reconnect loop's next `notified()` wait can then immediately fire once more and issue one extra, instantly-successful "reconnect" against the already-healthy connection. Confirmed via manual testing (see below) — this shows up as one harmless extra `Reconnected.` log line, not a functional problem, and wasn't judged worth the added complexity of a generation counter or similar to fully close (per this project's usual "don't over-engineer past a concrete need" stance).

`client::main`'s `open_connection` now parses the connection string into a `ConnectionTarget` once (rather than a raw string) and reuses `client::reconnect::redial` for its own one-shot startup connect too, so the dispatch logic isn't duplicated between the startup path and the reconnect path — the startup path still prints the TLS fingerprint once and still panics if the *first* connection attempt fails outright (an unreachable server at process start is still treated as fatal, unlike a connection that broke after having been established).

**Manually verified end-to-end** against real `client`+`server` binaries over real TCP (`examples/` files, see below), reproducing the exact scenario the user reported: started both, `kill -KILL`'d the server mid-poll (not a graceful shutdown, to match "the server abraucht"), watched every one of the 5 poll functions immediately start logging `Broken pipe (os error 32)` every poll tick *and* the reconnect loop kick in immediately with `Connection lost — attempting to reconnect...`, backing off through `Connection refused` at 1s/2s/4s/8s/16s while polling kept right on failing/logging in parallel (not blocked). Restarted the server — the next backoff attempt succeeded (`Reconnected.`), including the one expected extra spurious reconnect cycle described above. Polling resumed on its own (no client restart): a value written directly on the server appeared on the client's mirror on the next poll, and a client-side staged `transactions/`+`TRANSACTION_END` write round-tripped successfully and was reflected on the server, exactly as before the outage.

## Pluggable data-representation layer — FUSE vs. flat files (resolved and implemented 2026-09-29)

**Motivation:** the FUSE layer was originally as much an experiment ("can this be built as a from-scratch filesystem at all") as a deliberate architecture choice, and in practice it turned out to carry real, structural problems inherent to how FUSE works, not implementation bugs to patch: every single `read()`/`write()`/`getattr()` round-trips from the calling process through the kernel VFS into this project's own userspace FUSE daemon and back, and the daemon has to hand-reimplement filesystem semantics (partial reads across multiple syscalls, concurrent open/read/write interleaving, atomicity of a value's content across one read) that a real filesystem already gets right by construction.

What's **not** given up: `holding-registers/Tank_Temperature` is still a real file a technician can `ls`/`cat`/`echo >` from any tool that already understands files — Dolphin, a shell script, `watch cat`, no bespoke client needed. Both representation layers present the *exact same* directory shape at the same paths; only how that shape is served differs.

**Core idea: stop reimplementing what the kernel already does correctly.** A second presentation layer, `datafs::flatfile`, renders Modbus data as real regular files on a real filesystem — any directory the operator points at (`--data-representation-layer files`'s `<root>` argument; `/run/...` gets tmpfs/RAM semantics for free if the operator wants that, but nothing here manages a tmpfs mount itself — the layer is named `files`, not `tmpfs`, deliberately, for exactly this reason) — kept current via `inotify` and atomic `rename()` instead of a custom `fuser::Filesystem` implementation.

**Confirmed: the Modbus-facing half of the codebase needed zero changes.** `client::transaction_consumer`/`server::transaction_consumer`, `client::polling`, `server::handler`, and the entire `protocol` crate only ever depended on `datafs`'s stores (`MachineStores`/`RegisterStore`/`CoilStore`/etc.) and the `(machine_name, HashMap<String, StagedValue>)`-tagged channel — none of it ever knew FUSE existed, and none of it had to change to support a second presentation layer. This was the design's central bet and it held completely through implementation.

**Crate rename:** `fuse-fs` → **`datafs`**, workspace-wide, mechanical (M1). One deviation from the original design text: no `datafs::stores`/`datafs::fuse` module split happened — `filesystem.rs` (the FUSE code) and the store types in `lib.rs` stayed exactly where they were; `flatfile.rs` was just added as a new sibling top-level module. The planned split would have been a large, low-value mechanical change with no functional benefit; revisit only if the flat module layout actually becomes confusing in practice, not preemptively (Extraction-Based Programming).

**Read side — `datafs::flatfile`'s renderers (M2/M3/M6/M7):** `FlatfileRegisterRenderer`/`FlatfileCoilRenderer`/`FlatfileDiscreteInputRenderer`/`FlatfileInputRegisterRenderer` (near-identical, sharing a `render_named_files` helper), `FlatfileFileRecordRenderer` (nested `<file_number>/<record_number>` directories), `FlatfileReportRenderer` (a real gap found only while starting M8 — `report/` had been missed entirely by M2/M3, backfilled before M8 could apply permissions to something that had to exist first), `write_server_id_file`/`write_machine_server_id_file` (a one-shot write, no renderer struct needed for something written exactly once), and `FlatfileClientTrustRenderer` for the root-level, server-only `client-trust/` subtree. Every renderer writes to `<name>.tmp` then `rename()`s over the real path — POSIX-atomic within one directory, so a concurrent reader always sees either the fully-old or fully-new content, regardless of content size. `MachineFlatfileReaders` (M6) bundles one machine's five per-machine renderers rooted at `<root>/<machine_name>/`; multi-machine layout needed **no inode-stride trick** the way FUSE's own multi-machine work did — real nested directories already namespace themselves for free, proven by a dedicated test (two machines, same register name, different values, no leakage).

**Change detection — a plain poll, not the originally-planned `Notify`.** The design text described push-based change detection (a `Notify` on `MachineStores`, fired by every `.set()`). Implementing that would have meant touching every `store.set()` call site across `client`/`server` (reconnect polling, transaction consumers, direct-write handlers) — well outside `datafs::flatfile`'s own scope. What shipped instead: every renderer exposes a plain `render_once()`; `client`/`server` `main.rs` (M9) call it on a **200ms `tokio::time::interval`**, purely local, never gated on a Modbus round trip — which is what actually answers the original "round trips on real-time systems" complaint. Each renderer also caches its last-rendered content per entry, so an unchanged value costs no syscalls on a given tick. Revisit the `Notify` approach only if 200ms polling is ever shown to be insufficient in practice.

**Write side — `inotify`, not `write()`/`release()` (M4/M5).** `FlatfileTransactionWatcher` (client) watches `transactions/` for `IN_CLOSE_WRITE` (stage) and `IN_CREATE` of `TRANSACTION_END` (commit + drain + clear the real directory), draining into the exact same channel `transaction_consumer` already reads — reuses the parsing functions (`parse_register_value`/`parse_masked_register_value`/`parse_coil_value`/`parse_file_record_name`/`parse_file_record_value`) extracted out of `filesystem.rs`'s `MachineFs` into `lib.rs` as free functions during M4, so both presentation layers share identical staging logic instead of two copies drifting apart. `FlatfileDirectWriteWatcher` (server) watches every directly-writable directory for `IN_CLOSE_WRITE` and sends each write as its own implicit one-item transaction immediately — no staging ritual, mirroring `WriteMode::Direct` exactly, including per-type dispatch precedence and `StagedValue` variants. Two distinct types rather than one `WriteMode`-parameterized type, unlike `MachineFs` — lets the type system rule out "client accidentally does a direct write" at compile time rather than a runtime check.

**The detail that prevents a feedback loop, without tagging event origin:** the renderers' own updates go through `rename()`, which the kernel reports as `IN_MOVED_TO`, never `IN_CLOSE_WRITE`. A genuine user write (`echo`, an editor) always goes through `open()+write()+close()` — `IN_CLOSE_WRITE`, never `IN_MOVED_TO`. Watching only `IN_CLOSE_WRITE` on writable paths therefore structurally can't mistake the renderer's own writes for user input — verified directly by the M4/M5 test suites, not just asserted.

**A real, documented capability gap, not fixed (two instances):** (1) FUSE's `create()` can reject an unknown `transactions/<name>` target immediately (`ENOENT`, so `echo` itself fails); a real filesystem has no such hook, so `echo` always succeeds under `files` and the stray file is only removed *after* the fact, at `IN_CLOSE_WRITE` time (`FlatfileTransactionWatcher`/`FlatfileDirectWriteWatcher`'s own doc comments). (2) `AccessRight`-based read-only enforcement for `holding-registers/<name>` on the server (M5) is application-level only for the same reason (echo already succeeded before the watcher can react) — unlike `client-trust/`'s permissions (below), which genuinely are kernel-enforced, because those are a fixed mode set once per render rather than a per-register right that has to survive being reset by every atomic-rename swap.

**Permissions (M8):** `fuse-permissions.toml`'s `mode`/`uid`/`gid` become real `chmod`+`chown` (`datafs::flatfile::apply_directory_permissions`, `chown` via raw `libc::chown` since `std::fs` has no portable one) on `holding-registers/`/`coils/`/`report/`/`transactions/` — exactly `FusePermissions`'s own existing scope, nothing more. `client-trust/` and everything under it is unconditionally `chmod`'d `0o700` (dirs) / `0o400` (files), matching CLAUDE.md's own "hardcoded to maximum restriction" requirement for real. **Documented gap:** a real `chown()` needs `CAP_CHOWN` to set an owner other than the calling process's own UID, unlike FUSE's `getattr`, which can report any uid/gid with zero privilege since it's synthetic data the kernel just passes through — configuring a non-default `uid`/`gid` will genuinely `EPERM` unless the server process has that privilege. The common case (mode-only overrides) never hits this, since unset `uid`/`gid` default to the process's own real ones.

**CLI wiring (M9):** `--data-representation-layer <fuse|files>` on both `client` and `server`, **`files` is the default** — a deliberate breaking change to the previous all-FUSE default, same stance as every other breaking default in this file. No separate `--data-dir` flag was added — the existing positional mountpoint argument was simply renamed `<root>` in both usage strings, since it means the same thing structurally either way. On clean shutdown (Ctrl+C/SIGTERM), the `files` backend `remove_dir_all`s the whole `<root>` tree, mirroring FUSE's `umount_and_join` — a real directory doesn't vanish on its own the way a FUSE mount does.

**Manually verified end-to-end** over real TCP (throwaway device description + `server-options.toml`, both deleted after use): the `files` directory tree matched the FUSE layout exactly at every level (`PumpA/holding-registers/`, `coils/`, ..., root-level `client-trust/` at `0700` with its two `0700` subdirectories); a direct write to the server's `holding-registers/Tank_Temperature` propagated to the client's own mirror on the very next poll tick; a client-staged `transactions/Tank_Temperature` + `TRANSACTION_END` produced a real Modbus write, `report/Tank_Temperature` showed `OK`, and the server's own copy updated immediately; both processes removed their root directory and exited cleanly on SIGTERM. `--data-representation-layer fuse` was re-verified working unchanged in the same session (real `/dev/fuse` mount, clean unmount) — no regression in the pre-existing FUSE path.

**Known loose end, not yet addressed:** the `--fuse-permissions` flag name now applies to both backends (real `chmod`/`chown` under `files`, kernel enforcement under `fuse`) but kept its FUSE-specific name — deliberately not renamed alongside M9 to avoid touching every usage string/doc reference twice in one milestone; a rename to something backend-neutral (e.g. `--data-permissions`) remains a candidate follow-up.

## MQTT (Sparkplug B) representation layer (design resolved 2026-09-30, M1-M9 implemented 2026-09-30, M10 TCK conformance complete 2026-10-01 — `SessionEstablishmentTest` passes every assertion it runs)

**Motivation:** after using both `fuse` and `files` in practice, the user judged that a local filesystem projection — either backend — isn't the right representation for this project's data after all: real races and round-trip overhead persist in some form under both (see the `files` backend's own documented gaps above). Rather than a third filesystem-shaped backend, this is a genuinely different representation: MQTT, with **Sparkplug B** as the wire schema.

**Architecture:** `MQTT Broker <-> client <-> server`, with the broker **embedded directly in the `client` binary** (not a separate always-on service the user has to run) — chosen so a technician still just runs one binary, matching this project's existing "one binary, no extra infrastructure" ergonomics. The `client`↔`server` link is unchanged — still real Modbus (TCP/RTU/TLS). `client` fetches the device description at startup exactly as it does today (FC43 or local TOML fallback) and, in this new layer, additionally translates it into Sparkplug B session/metric data instead of (or alongside) building a `fuse`/`files` tree.

**Server-side data-update problem, resolved separately as "Option C" (library core + thin daemon, FFI deferred):** the question of *how the server's own dataset gets updated* (distinct from the client↔server Modbus link) was treated as its own design problem, informed by real prior art:
- Researched how existing Modbus server/slave implementations solve this: `pymodbus` (`ModbusSlaveContext.setValues`/`getValues`) and `libmodbus` (`mb_mapping->tab_registers[i]` direct array access) both assume the "real device logic" runs **in the same process** as the Modbus slave stack — no cross-process interface exists or is needed in the common case. Where cross-process *was* needed, real examples split into exactly two patterns: a **REST API** (`ModbusSim`, the `gplug-ems` simulator) or a **watched/polled file** (`lab240/modbus-slave`'s "file mode" — periodic *pull*, notably not `inotify`-driven push, a real contrast to this project's own `files` backend). No real-world example uses MQTT to feed a slave's own dataset — every MQTT↔Modbus bridge found (`modbus4mqtt`, Modbus Tester) sits on the **master/gateway side**, i.e. our `client`'s role, never the slave/`server`'s.
- Decision: **`ServerHandle`**, a plain safe-Rust library (no `unsafe`, no FFI) wrapping the same `MachineStores` + validation logic already used by `transaction_consumer`/`MachineFs::release()`/the flatfile watchers today — one place implementing "set a register by name, validated against the `DeviceDescription`, synchronous `Result`" instead of that logic being duplicated/scattered across FUSE, flatfile watchers, and the transaction consumer. `server`'s binary becomes a thin wrapper: `ServerHandle` + the Modbus listener + a small local Unix-socket/REST daemon on top that just forwards requests into the same handle (this daemon is effectively `files`' replacement on the server side, using the "REST/socket API" pattern real prior art actually converged on, not the file-watching pattern this project's own `files` backend used).
- An FFI (`cdylib`) shim exposing `ServerHandle` via a C ABI — for embedding the server's core directly into a host process (e.g. a C/C++ device simulator, zero-IPC, matching `libmodbus`'s own embed-in-your-process precedent) — is **explicitly deferred**, not ruled out: building it now would mean `unsafe extern "C"` boundary work (pointer lifetimes, `CStr` round-trips, `catch_unwind` at every entry point since a Rust panic unwinding across FFI is UB) for a consumer that doesn't exist yet. Per Extraction-Based Programming, `ServerHandle`'s safe Rust API already gives any **Rust** embedder zero-overhead in-process access without touching `unsafe` at all; the FFI shim is a thin adapter to add later, once a concrete non-Rust host actually needs it.

**TOML schema additions (per-value and per-machine), motivated by MQTT/Sparkplug consumers but generally useful beyond MQTT:** researched three real MQTT self-description conventions (Homie 5, Sparkplug B, Home Assistant MQTT Discovery) for what metadata they carry beyond raw name+datatype, and adopted every recurring field the user judged useful for a technician's decision-making — this directly resolves Milestone E1's old deferred "scaling/units... until a concrete consumer needs them" note; MQTT is now that consumer.
- **Per value** (register/coil/discrete-input/input-register): `unit` (physical unit, e.g. `"°C"`), `device_class` (semantic category — reuse Home Assistant's existing controlled vocabulary rather than invent our own, since it's become a de-facto standard even outside HA), `format`/valid range (Homie's `"-20:120"`-style hint), `display_name` (separate from the existing `name`, which stays the machine-safe identifier used for FUSE paths/topic segments/transaction keys — Homie and HA both separate technical ID from human label, we currently don't), `icon`, `precision` (display decimal places, mainly for `f32`/`f64`), `state_class` (`measurement`/`total`/`total_increasing` — matters for any consumer doing long-term statistics, e.g. a counter register should be `total_increasing` not `measurement`), `expire_after` (staleness threshold — genuinely useful independent of MQTT too, ties naturally to the existing `ReconnectSignal`/poll-interval machinery for detecting a stuck connection).
- **Per machine** (`[[machines]]`): `manufacturer`, `model` (mirrors Sparkplug/HA's device-grouping metadata), plus an availability/online concept fed by the client's existing `ReconnectSignal` — maps naturally onto Sparkplug's NBIRTH/NDEATH lifecycle (see below).
- All new fields are optional; omitting them preserves today's behavior exactly. `AccessRight` already covers Homie's `settable`/HA's implicit writability — no new field needed there.

**MQTT schema format: Sparkplug B, chosen over Homie 5 and Home Assistant Discovery — decided from evidence, not preference.** Researched which format a real Node-RED user in an industrial setting would actually reach for (the concrete scenario the user posed): Sparkplug B has an official FlowFuse (the company behind commercial Node-RED tooling) implementation guide, actively maintained `node-red-contrib-mqtt-sparkplug-plus`, and real integration guides tied to specific industrial PLC hardware (CLICK PLUS/Productivity PLC) plus Ignition/Opto22 forum activity — all squarely in this project's own target audience. Homie's Node-RED packages are more fragmented/less mature (one at v0.1.9) and its own community trends toward smart-home, not industrial — telling detail: one Homie Node-RED package exists specifically to *translate Homie into Home Assistant Discovery*. Home Assistant Discovery itself was ruled out early: its entity model is built for smart-home dashboards, not raw industrial register data, and it has no real presence in industrial Node-RED usage at all. This reverses an earlier lean toward Homie (simpler, no protobuf) — ecosystem fit for the stated real-world use case won out over implementation simplicity.

**Dependency choices — broker external, Sparkplug B protocol self-implemented:**
- **Embedded broker: `rumqttd`** (`bytebeamio/rumqtt`) — confirmed actively maintained (v0.20.0, ~184k downloads, repo commits into 2026, sibling crate `rumqttc` released as late as November 2026), pure Rust, purpose-built for embedding. Using an external crate here follows the same reasoning as `rustls` for TLS: broker/transport infrastructure isn't this project's "from scratch" core competency (Modbus is), so no reason to reinvent it.
- **Sparkplug B protocol itself (protobuf payload codec + session/topic/sequence semantics): self-implemented, not `lb-sparkplugb-rs`/`sparkplug-rs`/`srad`.** Evaluated all three: `lb-sparkplugb-rs` was rejected outright as immature (v0.1.1, 30 downloads, no linked repository, explicitly "(phased)" with Edge/Host roles admittedly incomplete) — not a maintenance-risk judgment call, a clear "not ready" one. `sparkplug-rs` (mature, 14k+ downloads, real repo) and `srad` (fuller framework, actively maintained, includes an `srad-client-rumqtt` integration crate) are both genuinely viable, not maintenance-risks — the user chose to self-implement anyway once informed of this, reasoning that unlike TLS, Sparkplug B's protobuf encoding is **not cryptography** — the specific danger class that justified reaching for `rustls` instead of hand-rolling TLS doesn't apply here. Encoding a fixed, publicly-documented message schema (not general-purpose protobuf) was judged comparable in scope to this project's existing from-scratch PDU/RTU-CRC16 work. **Explicitly flagged, independent of this choice:** the harder part of Sparkplug B conformance is session semantics (`seq`/`bdSeq` sequencing, NBIRTH/NDEATH/rebirth handling) which `sparkplug-rs` wouldn't have covered either way (raw protobuf bindings only) — only `srad` would have, and that's exactly where `srad`'s smaller community made the user least comfortable depending on it. So the self-implementation decision doesn't remove this conformance burden — it was never avoidable by picking a crate other than `srad`.
- **No pluggable schema-format abstraction yet, deliberately.** Unlike `fuse`/`files` (which had two concrete implementations in the plan from day one, making the shared `--data-representation-layer` boundary a real extraction, not a speculative one), Sparkplug B is currently the *only* concrete schema-format implementation planned — Homie or others remain hypothetical. Per Extraction-Based Programming, the Sparkplug-specific code should live cleanly isolated in its own module (candidate: `client::mqtt::sparkplug` or a new crate), but no generic `SchemaTranslator`-style trait gets built until a second concrete format is actually being implemented — building one now, with a single implementor, risks guessing its shape wrong.

**Resolved 2026-09-30: `mqtt` becomes a third coexisting `--data-representation-layer` option, not a replacement.** `fuse`/`files` stay exactly as they are — no removal, no forced migration. However, from this point on `fuse`/`files` are considered **legacy**: new features land on the `mqtt` layer going forward, `fuse`/`files` only get bugfixes, not new capability. This settles what M9 (CLI wiring) actually does — add a third variant, not deprecate the existing two.

**Milestone plan, agreed 2026-09-30 (same granularity as the multi-machine 6-step / datafs 10-milestone plans):**
- **M1 — Protobuf wire format, from scratch.** Only the fixed Sparkplug `Payload`/`Metric`/`PropertySet` message set (not general-purpose protobuf) — varint, length-delimited, fixed32/64 encode+decode, own fuzzer entry mirroring `protocol`'s.
- **M2 — Sparkplug's own data model, self-contained within the `sparkplug` crate.** Sparkplug's `DataType` enum (all 35 codes) and `MetricValue` (the scalar `Metric.value` oneof shape: Int/Long/Float/Double/Boolean/String/Bytes — `dataset_value`/`template_value`/`extension_value` not modeled, no concrete need for composite/array values). **Revised 2026-09-30, during implementation:** the original scope here also included mapping our own `protocol::DataType`/`RegisterValue`/`CoilValue` onto these Sparkplug types — moved to M5 instead, so `sparkplug` stays a self-contained protocol crate with no dependency on `protocol`/`datafs`, mirroring how `protocol` itself has no `datafs` dependency. That mapping is real glue code belonging in `client`, not in the reusable protocol implementation.
- **M3 — Topic namespace & MQTT plumbing.** `spBv1.0/<group_id>/<message_type>/<edge_node_id>/[<device_id>]`; resolves how `client` — which hosts the broker itself — also acts as an Edge Node MQTT client of its own embedded broker (loopback connection), needed to use the broker's own Will/LWT mechanism cleanly for `bdSeq`/NDEATH (see M4).
- **M4 — Session lifecycle: NBIRTH/NDEATH.** `bdSeq` set via the MQTT Will payload at connect time so it matches between the last NBIRTH and a later NDEATH; `seq` counter with 0-255 wraparound; one Edge Node identity per `client` instance.
- **M5 — DBIRTH/DDEATH per machine.** Each configured machine = one Sparkplug Device under the one Edge Node (natural fit with the existing multi-machine model); full metric list + alias assignment built from `DeviceDescription` — this is the actual TOML→Sparkplug translator that motivated this whole design thread. **Now also carries the `protocol::DataType`/`RegisterValue`/`CoilValue` → Sparkplug `DataType`/`MetricValue` mapping**, moved here from M2 (see M2's note) — this mapping lives in `client`, not in the `sparkplug` crate.
- **M6 — NDATA/DDATA.** Incremental value publishing on change, alias-referenced, tied into the existing polling/store-update cycle.
- **M7 — DCMD (write path).** Subscribe to the command topic, decode incoming metric writes, feed them into the existing `(machine_name, StagedValue)` channel — reuses the transaction-consumer infrastructure unchanged, same "new frontend, zero changes to the Modbus-facing half" bet that held for `datafs::flatfile`.
- **M8 — Rebirth handling.** Respond to a `Node Control/Rebirth` command by republishing NBIRTH/DBIRTH — required for spec conformance, not optional polish.
- **M9 — CLI wiring.** Resolve the open replace-vs-coexist question above first; then wire the new layer in (new flag value or a breaking removal of `fuse`/`files`), embed `rumqttd`, wire the Edge Node logic into `client::main`. Also implement the `server`-side `ServerHandle` + local socket/REST daemon in this pass (the two halves of this whole design landing together).
- **M10 — Sparkplug TCK conformance testing.** The TCK is **not** a `cargo test` component — it's an external tool (a Node.js/yarn web console plus its own bundled HiveMQ broker + extension). `client`'s Edge Node logic must be able to target an **external** broker (the TCK's HiveMQ instance) for this test, not only its own embedded `rumqttd` — a real deviation from normal operation worth designing for explicitly in M3/M9, not bolted on later. Results land in `SparkplugTCKResults.log`; fix any conformance gaps found until the Edge Node profile passes. **Not yet done** — the only milestone remaining from this plan.

**M1-M9 implementation notes:**

- **`sparkplug` crate (M1/M2):** from-scratch protobuf primitives (`wire`: varint/length-delimited/fixed32/fixed64, bounded varint decode, own fuzzer mirroring `protocol`'s), Sparkplug's `DataType` (all 35 codes) and `MetricValue` (7 scalar oneof variants — Int/Long/Float/Double/Boolean/String/Bytes; DataSet/Template/extension not modeled), `Metric`/`Payload` message-level encode/decode (`metric.rs`/`payload.rs`, built in M4 once a real gap surfaced: M1/M2 had wire+data-type primitives but no message layer connecting them), `SeqCounter`/`BdSeqCounter`, `topic::build_topic` (rejects a device-scoped type built without `device_id` and vice versa via `Result`), `session::build_nbirth_payload`/`build_ndeath_payload`/`build_dbirth_payload`/`build_ddata_payload`/`build_ndata_payload`/`build_ddeath_payload` (`NBIRTH` resets `seq` to 0; every other data/birth message continues the one running counter; `NDEATH` alone carries `seq: None`, delivered via the MQTT Will rather than actively published). `sparkplug` has zero dependency on `protocol`/`datafs` — the Modbus↔Sparkplug mapping lives entirely in `client` (moved there from an original M2 draft that would have put it in this crate).
- **`client::broker`/`client::edge_node` (M3/M4/M8):** `start_embedded_broker(BrokerConfig)` runs `rumqttd` on its own thread from a hand-rendered TOML config (`rumqttd::Config` is only ever built via its own `Deserialize` impl, never hand-constructed); `BrokerConfig::parse` (M9) makes every one of its 7 tuning fields overridable via `--mqtt-broker-config <path.toml>`. `connect_edge_node` dials that broker over loopback as the Edge Node's own MQTT client, registers `NDEATH`+`bdSeq` as the MQTT Will *before* connecting, publishes `NBIRTH` right after. The same background task that keeps `rumqttc`'s event loop polled also picks out `DCMD`/`NCMD` publishes by topic and forwards them into `dcmd_receiver`/`ncmd_receiver` — no second consumer of the one `AsyncClient`/`EventLoop` pair. `EdgeNodeConnection` retains its connect-time `bd_seq` so a later `Rebirth` request republishes `NBIRTH` with the same `bdSeq`, only `seq` reset to 0 (`publish_nbirth`, reused by both the initial connect and any later rebirth). **Known gap, not yet solved:** `bdSeq`/`NBIRTH` handling across an internal `rumqttc` reconnect after a real connection drop.
- **`client::sparkplug_alias`/`sparkplug_translator` (M5/M7):** `AliasAllocator` assigns one `u64` per `(machine_name, metric_name)` (aliases must be unique per spec across the whole Edge Node, but the same metric name can legitimately repeat across machines) and its reverse `metric_for_alias` (added in M7, once resolving an incoming `DCMD`'s alias-only identification needed it). `map_data_type`/`map_register_value`/`map_coil_value` convert `protocol`/`datafs` types to Sparkplug ones (`U24`/`I24` fold onto `UInt32`/`Int32`, signed values are sign-extended then bit-reinterpreted into the wire's unsigned slot); `metric_value_to_register_value`/`metric_value_to_staged_value` (M7) are the inverse, resolving an incoming write and rejecting a mismatched value shape, an unknown name, or a read-only target (discrete-inputs/input-registers, exactly like every other write path). `build_machine_metrics` assembles one machine's full metric list (current-or-default value, per-metric alias) — what a `DBIRTH` carries.
- **`client::sparkplug_change_tracker` (M6):** `ChangeTracker` diffs a freshly-built metric list against what it last recorded, keyed by alias (globally unique, so one flat map covers every machine), returning only genuinely-changed-or-new metrics — what makes `NDATA`/`DDATA` "incremental" rather than a full re-birth every tick.
- **`client::sparkplug_command` (M7/M8):** `decode_dcmd_metrics` resolves each metric in an incoming `DCMD` independently (unknown alias, wrong machine, unresolvable name, or wrong value shape is logged and skipped — one bad entry never blocks the rest of the message, mirroring `transaction_consumer`'s own "unknown machine: log and drop" precedent), then `run_dcmd_forwarder` forwards resolved writes into the **exact same `std::sync::mpsc::Sender<(String, HashMap<String, StagedValue>)>`** `transaction_consumer` already reads from everywhere else in this project — a real bug (writing it against `tokio::sync::mpsc` instead) was caught and fixed before M9 wiring made the mismatch unavoidable. `is_rebirth_request`/`run_rebirth_handler` (M8) recognize the spec's well-known `"Node Control/Rebirth"` metric (by name, never alias — it's outside the translated alias space) and republish `NBIRTH` then a fresh `DBIRTH` per machine.
- **Real, cross-cutting fix found in M7:** `sparkplug::metric::decode_metric` originally required `name` unconditionally, but a spec-conformant `DCMD`/`DDATA` from a real host application typically carries only `alias` once a prior `BIRTH` established the mapping — such a message would have failed to decode entirely. Fixed: a metric decodes fine with either `name` or `alias` present (`DecodeError::MissingIdentifier`, only raised when *both* are absent); a metric with no `name` field decodes with `name: String::new()`.
- **M9, client half — `client::main`:** `--data-representation-layer mqtt` starts the broker, connects the Edge Node, subscribes to `NCMD` once and every machine's `DCMD`, publishes one `DBIRTH` per machine (seeding that machine's `ChangeTracker` with the same metric list so the first periodic tick doesn't immediately re-publish everything as `DDATA`), spawns `run_dcmd_forwarder`/`run_rebirth_handler` sharing the same `transaction_sender`/`machine_stores` every other layer already uses, and spawns one periodic per-machine task (on `poll_interval`, tying `DDATA` to the existing polling cadence per this design's own M6 note) that diffs and publishes only changed metrics. New flags: `--mqtt-broker-config`, `--mqtt-group-id`/`--mqtt-edge-node-id` (defaults `"infused_modbus"`/`"client"` — must be overridden for more than one `client` instance against the same broker/host app). `<root>` is unused under `mqtt`.
- **M9, server half — "Option C" (`server::server_handle`/`data_daemon`):** `ServerHandle` is a plain safe-Rust library (no `unsafe`, no FFI — the FFI shim stays explicitly deferred, not built) wrapping `MachineStores` behind validated, synchronous, name-based `set`/`get`. Writes go **directly through the same `Arc<Mutex<_>>` stores** every other writer already locks, *not* through `transaction_sender`'s channel — that channel's real job is letting FUSE's `write()`/`release()` callbacks hand off without blocking the kernel on a lock held elsewhere, which doesn't constrain a plain synchronous library call; the `Mutex` each store already wraps is what keeps a `ServerHandle` call and a concurrent channel-drain from `transaction_consumer` mutually exclusive, no new mechanism needed. `server::data_daemon` serves this behind a Unix domain socket (`server-data.sock`) mirroring `admin.rs`'s shape line-for-line (`0600` mode, `SO_PEERCRED`-gated, line protocol: `SET <machine> <point> <value...>` / `GET <machine> <point>`) — `server::peer_auth` (`server_uid`/`is_authorized_uid`) was extracted out of `admin.rs` first, once a second call site needed the exact same security-relevant check. `--data-representation-layer mqtt` on `server` skips the FUSE/flatfile tree entirely and serves this socket instead, over the same `machine_stores` the wire-facing `handler.rs` already writes into — so an external Modbus master's write and a `SET` over the socket are always looking at the same data. `<root>` is unused.
- **Verified end-to-end with real processes, both halves independently** (the client's Sparkplug layer and the server's `ServerHandle` daemon are two separate mechanisms per the "Option C" design, never talking to each other directly): real NBIRTH/DBIRTH/DDATA/DCMD/rebirth observed over real TCP by an independent MQTT subscriber and confirmed against a real `server`; a real `server --data-representation-layer mqtt`'s socket (`socat -  UNIX-CONNECT:server-data.sock`) round-tripped `SET`/`GET`, rejected an unknown point, and a second independent real `client` (`files` layer) polling the same server over real Modbus read back exactly the values set through the socket.

**The TCK's "Session Establishment" test caught a real, genuine conformance bug**, not a tooling artifact: `bdSeq` was generated fresh via `BdSeqCounter::new()` inside `connect_edge_node` on every `client` process start, so every restart produced the exact same value (`0`) instead of one higher than the previous session's — defeating `bdSeq`'s entire purpose (letting a Host Application tell a genuinely new session's `NBIRTH` apart from a stale `NDEATH`, delivered late via the MQTT Will, belonging to an already-superseded session). Confirmed failing directly against the TCK's own `topics-nbirth-bdseq-increment` and `message-flow-edge-node-birth-publish-will-message-payload-bdSeq` assertions (`Actual bdseq: 0 expected bdseq: 1`). **Fixed** with a new `client::bd_seq_persistence` module: reads the next `bdSeq` from a small file (`client-mqtt-bdseq`, next to the process's cwd, same "fixed default path" precedent as `client-tls-identity/`), persists `current + 1` back atomically (temp-file-plus-rename) before use — falls back to `0` and logs a warning on any I/O failure rather than refusing to start. `connect_edge_node` now takes `bd_seq: u64` as a caller-supplied parameter instead of generating it internally; `BdSeqCounter` (still in the `sparkplug` crate, still tested there) is no longer used by `client` at all, since it could only ever produce one value per process anyway (this project has exactly one Edge Node identity per `client` instance) — the real missing piece was cross-*process* persistence, `client`-side I/O the protocol-only `sparkplug` crate has no business owning. **Verified directly against the real TCK**: multiple clean connect/disconnect cycles after the fix produced zero assertion failures from the same extension that reliably flagged the bug before it, confirmed by watching `docker logs` in real time across several restarts.

**The web console's "start test" action never reliably worked** across two whole sessions of trying (`TCK.java`'s own `newTest()` log line never appeared despite the UI showing "running") — not a conformance gap, an interaction-model problem with the console itself. **Resolved 2026-10-01 by bypassing the console entirely**: reverse-engineered the TCK's real control protocol straight from its own Java source (`PublishInterceptor.java`/`Constants.java`, both present in the built Docker image) — the console is *itself* just an MQTT publisher on `SPARKPLUG_TCK/TEST_CONTROL` (`"NEW_TEST EDGE SessionEstablishmentTest <hostApplicationId> <groupId> <edgeNodeId> [deviceIds...]"` / `"END_TEST"`), with results/log lines published back on `SPARKPLUG_TCK/RESULT`/`SPARKPLUG_TCK/LOG` (or just visible directly in `docker logs`). A throwaway `client/examples/tck_control.rs` (`rumqttc`-based, `start`/`stop`/`watch` subcommands) drives this directly — no browser, no `claude-in-chrome`, needed at all. This also explained every earlier "Test end requested but no test active" failure: `SessionEstablishmentTest` auto-ends itself the instant it observes one full NBIRTH+DBIRTH sequence, often before a human can click "Stop Test" at all.

**Full real reports obtained this way caught three more genuine conformance bugs**, beyond the `bdSeq` one above, all fixed same-session (2026-10-01):
1. **QoS.** `client::edge_node`'s active publishes (`publish_nbirth`/`publish_dbirth`/`publish_ddata`/`publish_ndata`/`publish_ddeath`) were all sent at `QoS::AtLeastOnce`; spec requires `QoS::AtMostOnce` (QoS 0) for every one of them. The MQTT Will carrying `NDEATH` stays at `QoS::AtLeastOnce` — confirmed correct separately, untouched.
2. **Missing `Node Control/Rebirth` metric in `NBIRTH`.** Every `NBIRTH` must include this metric (`DataType::Boolean`, value `false`, **no alias** — deliberately excluded from `AliasAllocator`'s translated alias space, unlike every Modbus-derived metric). Added via `sparkplug::session::rebirth_metric`.
3. **Missing per-metric `timestamp`.** `sparkplug::metric::Metric` only modeled the payload-level timestamp, not the **per-metric** one (wire field 3, confirmed against the real `sparkplug_b.proto`) spec requires on every metric in `NBIRTH`/`DBIRTH`/`NDATA`/`DDATA`. Added as `Metric.timestamp: Option<u64>`; `client::sparkplug_translator::build_machine_metrics` and `sparkplug::session`'s own `bd_seq_metric`/`rebirth_metric` now stamp it from the same wall-clock source `edge_node` already used for the payload-level one.

**A fourth, distinct finding — not a bug, a missing capability — surfaced only once the above three were fixed and the test ran further: `message-flow-edge-node-birth-publish-phid-wait`.** Per spec, an Edge Node configured to wait for a specific Primary Host Application MUST verify it's online (via that host's own retained `spBv1.0/STATE/<host_id>` message) before publishing `NBIRTH`/`DBIRTH` — a capability this project had never implemented at all (previously `sparkplug::topic`'s own doc comment explicitly said the `STATE` topic form "isn't needed" since this project only ever builds an Edge Node, never a Host Application — true for *publishing* `STATE`, but it still needs to *subscribe* to one). **Implemented:** `sparkplug::topic::build_state_topic(host_id)` (the one topic form with no group/edge-node scoping); `client::primary_host_state::parse_online` hand-parses the `STATE` payload's `{"online":<bool>,...}` — plain JSON, unlike every other Sparkplug message, and small/fixed enough to scan by hand rather than pull in a JSON crate, matching this project's "from scratch for a bounded format" convention already applied to Modbus PDUs and Sparkplug's own protobuf. `connect_edge_node` gained an `primary_host_id: Option<&str>` parameter (new CLI flag `--mqtt-primary-host-id`, default `None` — most deployments have no Primary Host at all, so this is strictly opt-in and changes nothing for anyone not using it); when `Some`, it subscribes to that host's `STATE` topic and **blocks indefinitely** until an `online: true` message arrives, before publishing `NBIRTH` — no spec-mandated timeout exists, and inventing one would just mean publishing without the verification this parameter exists to provide. This wait happens *before* the DCMD/NCMD background-forwarding task is spawned (which takes ownership of the MQTT event loop), so the same loop can still be polled directly for the wait without a second competing consumer.

**Final result: `OVERALL: PASS but INCOMPLETE` — every single assertion `SessionEstablishmentTest` runs now passes.** "INCOMPLETE" is the test harness's own behavior, not a gap in this project's Edge Node: `SessionEstablishmentTest` self-ends after observing one NBIRTH+DBIRTH, before a second connect cycle could exercise `principles-persistence-clean-session-50`. Re-running this test from a future session should not expect a different outcome without the TCK's own test harness changing.

## Programmatic Rust API for `ServerHandle` — typed `set_*`/`get_*`, before any FFI layer (resolved and implemented 2026-10-01)

**Motivation:** the next planned step after `ServerHandle` (see "MQTT (Sparkplug B) representation layer" above) was originally framed as "build the `cdylib` FFI shim" — but the user clarified this explicitly: build a **pure Rust programmatic API first, deliberately without the FFI layer**, with the FFI shim coming later as its own separate step on top. The concrete requirement: an embedding Rust application should be able to pull `ServerHandle` directly into its own process (already possible — `ServerHandle::new` already takes a parsed `DeviceDescription` + the real `MachineStores`, no socket needed) and have it be **type-safe** — a register declared `u16` in the TOML should only accept a `u16` value, not an arbitrary string that happens to parse.

**Typed API added, one pair per point kind, operating on `datafs`'s own `RegisterValue`/`CoilValue` instead of raw strings:** `set_register`/`get_register`, `set_coil`/`get_coil`, `set_discrete_input`/`get_discrete_input`, `set_input_register`/`get_input_register`, `set_file_record`/`get_file_record` (the last still `Vec<u8>` — file records are vendor-specific opaque blobs, no narrower type to enforce). `set_register`/`set_input_register` validate the passed value's own `RegisterValue::data_type()` against the point's declared `data_type`, rejecting a mismatch with a new `ServerHandleError::TypeMismatch { expected, got }` — distinct from `InvalidValue`, which is about a string that doesn't parse at all, not an already-typed value of the wrong width. The original string-based `set`/`get` stay (still needed by `data_daemon`'s text-protocol socket) but now just parse `raw_value` and delegate to the typed methods — one place parses strings, one place validates, instead of the logic being duplicated across both.

**Listing/introspection methods added too, so a caller can discover what exists without hardcoding names:** `registers`/`coils`/`discrete_inputs`/`input_registers`/`file_records` return the machine's declared `&[RegisterDescription]`/`&[CoilDescription]`/etc. straight from its `MachineDescription` (no new struct needed — these types already carry name/address/data_type/access), plus `machine_names()`. Lets a developer write something like "for every read-write register, set it to its typed default" without a separate TOML-parsing step of their own.

**A real, pre-existing bug caught and fixed along the way, not a new design choice:** the original string-based `set` unconditionally rejected writes to discrete-inputs/input-registers with `ReadOnly` — this directly contradicted the already-shipped "server direct-write model" (see above), which makes both directly writable **locally on the server** (never over the wire, never on the client — but the server has nothing else to populate them, so local writes are how an operator/technician, or now an embedding program, provides what a real sensor would otherwise supply). Root cause: this logic was carried over unreviewed from before the typed API existed. Fixed by giving both real `set_discrete_input`/`set_input_register` methods; `data_daemon`'s socket inherits the fix automatically via the delegation above, no separate change needed there. The two tests that had locked in the old (wrong) behavior (`set_rejects_a_discrete_input`/`set_rejects_an_input_register`) were rewritten to assert the corrected behavior, not deleted.

**Scope: server-side only, this round** — the user confirmed this explicitly when asked. No client-side equivalent exists or is planned as part of this work. `server::server_handle` test count: 43 (up from 16 before this work). Still queued, unstarted, not combined with this step: the `cdylib`/C-ABI FFI shim (see above) — this typed API is explicitly the foundation it will build on later, not a replacement for needing it.

## `server-options.toml` — explicit per-function-code opt-in (design resolved 2026-09-18, implemented 2026-09-24)

Motivation: the goal is to eventually cover as much of the Modbus function-code space as practical (see the README's function-code support table for the full list and current status), but every function code `server` implements is attack surface it exposes to *any* reachable Modbus master, not just a trusted one — this is a `server`-only concern, since `client` only ever issues function codes it itself chooses to send, never accepts arbitrary incoming ones. This surfaced concretely while discussing FC 21 (Write File Record, 0x15): unlike every other FC implemented so far, a generic file-write primitive is dangerous less because of what it does on the wire and more because of what a server implementation might eventually back "file" with (e.g. if it were ever wired to something interpreted afterward, it becomes a remote config-injection primitive, not just a bad register value) — see the FC 21 discussion this section grew out of. Rather than deciding "implement it or don't" per FC, the resolution is to make *every* FC's availability an explicit technician choice.

**Schema:** a new `server-options.toml`, `[function-codes]` table, one boolean per function code, named after the operation rather than a code number (matches this project's existing snake_case TOML style, e.g. `mem-layout`, `access`):

```toml
[function-codes]
read_coils = false                     # 0x01
read_discrete_inputs = false           # 0x02
read_holding_registers = false         # 0x03
read_input_registers = false           # 0x04
write_single_coil = false              # 0x05
write_single_register = false          # 0x06
write_multiple_coils = false           # 0x0F
write_multiple_registers = false       # 0x10
report_server_id = false               # 0x11
read_file_record = false               # 0x14
write_file_record = false              # 0x15
mask_write_register = false            # 0x16
read_write_multiple_registers = false  # 0x17
read_fifo_queue = false                # 0x18
read_device_identification = false     # 0x2B / MEI 0x0E (FC 43)
```

The four out-of-scope serial-diagnostic FCs (0x07/0x08/0x0B/0x0C, see the FUSE/README notes on why they're excluded) never appear here — there's nothing to toggle for a FC that will never be implemented at all.

**Default policy: strict default-deny, explicit over implicit, no legacy exemption (confirmed 2026-09-18).** Every function code — including the ones already fully implemented today (Read/Write Coils, Read/Write Holding Registers, Write Multiple Coils/Registers, FC 43) — defaults to disabled unless its key is present and `true`. This is a deliberate behavior-breaking decision: an existing deployment adopting this feature must list what it actually needs, or the server rejects every single incoming request. Consistent with this project's general stance of accepting breaking changes rather than carrying compatibility shims while nothing is deployed yet (see the multi-machine schema section above for the same call made the same day).

**Unknown keys under `[function-codes]` are a hard parse error**, not silently ignored — same discipline as `fuse-permissions.toml`'s rejection of a `client-trust` key, so a typo doesn't leave a technician wrongly believing a function code is enabled (or disabled).

**CLI wiring:** `--server-options <path>`, optional — analogous to `--fuse-permissions <path>`. If omitted, behaves exactly like a present-but-empty file (everything disabled), not a startup error. Because "the server starts fine but answers nothing" is a real footgun for a forgotten flag, `server` prints a loud startup warning whenever zero function codes end up enabled.

**Wire behavior for a disabled FC:** the server responds with the same `ILLEGAL_FUNCTION` exception already used for a function code that isn't implemented at all — deliberately indistinguishable on the wire, so a remote peer can't fingerprint "implemented but disabled" apart from "never implemented" from the response alone.

**Composes cleanly with FC 43's existing fallback:** disabling `read_device_identification` needs no special-casing — the client's FC 43 fetch already treats every failure mode identically as "fall back to the local TOML", including an `ILLEGAL_FUNCTION` exception, which is exactly what a disabled FC 43 now produces.

**This is what makes FC 21 (Write File Record) implementable at all.** Its risk — a semantically-unscoped write primitive, more dangerous than an ordinary register write once/if "file" ever means something real — is mitigated by requiring an explicit technician opt-in rather than the on-by-default posture every other FC has had until now. No concrete use case for FC 21 exists yet; this mechanism just removes the reason it had to stay categorically out of scope.

**Implementation notes:** `server::server_options::ServerOptions` (own module, `server`-only — `fuse-fs`/`client`/`protocol` have no reason to know about it). Parsing mirrors `fuse_fs::permissions::FusePermissions` exactly (`RawServerOptions`/`RawFunctionCodes` as the actual `#[derive(Deserialize)]` targets with `deny_unknown_fields`, resolved into a plain public struct). The gate lives at the very top of `server::handler::handle_request` — before the existing function-code `match` — checking `server_options.is_enabled(function_code)` and returning the same `ILLEGAL_FUNCTION` `ExceptionResponse` the `match`'s own fallback arm already used for an unrecognized code, so both paths are genuinely indistinguishable on the wire, not just documented as such. `ServerOptions` is `Copy` (15 plain bools) and threaded through `server::connection::serve_tcp_connection`/`serve_rtu_connection` and `server/src/main.rs`'s `start_serving` the same way `MemLayout` already was — by value, no `Arc` needed. `#[cfg(test)] ServerOptions::allow_all()` exists purely so the ~40 existing `handle_request`/`serve_*_connection` unit tests (which predate this feature and test unrelated behavior) didn't all need a hand-written permissive TOML source. Manually verified against a real running `server` (raw-socket harness, deleted after use, same pattern as FC16/FC11/FC17's verification): no `--server-options` flag → startup warning printed, every request gets `ILLEGAL_FUNCTION` (FC3 confirmed); `--server-options` enabling only `read_holding_registers`+`write_single_register` → FC3 succeeds with a real value, FC1 (not enabled) still gets `ILLEGAL_FUNCTION`; an unknown key under `[function-codes]` panics at startup with a parse error, before any mount/bind happens.

## TLS transport security & client trust (resolved and implemented 2026-09-17/18)

**Documentation note (caught and fixed 2026-09-28):** this section was still headed "Planned... not yet implemented" and said "nothing in this section exists in code yet" long after the fact — stale from when the design was first captured, never updated once Milestones K through U actually shipped the same/next day. Everything below is real, current behavior — `server/src/tls.rs`, `client_trust.rs`, `admin.rs`, `persistence.rs`, `live_connections.rs` all exist and are wired into both binaries' `main.rs`. The one piece never actually completed is **T4** (manual verification that `fuse-permissions.toml`'s enforcement is real under a genuinely different UID) — every other milestone's manual check was performed, but T4 specifically needs a second real user account on the test machine, which was never available. Revisit that specific check before treating the FUSE-permissions half of this design as fully verified, independent of the code itself already being correct by inspection/review.

Motivation: Modbus TCP is unencrypted and trivially sniffable. A full CA-based TLS setup was rejected as too much certificate-management burden for a technician just trying to get two devices talking — this design gets real TLS's cryptography without a CA hierarchy, plus a way for a technician to control *which* clients may connect to a `server`.

**Transport is mutually exclusive.** A new connection-string scheme `tls+tcp://<address:port>` sits alongside `tcp://`/`rtu://`. A given `client`/`server` instance runs in exactly one of `tcp://`, `rtu://`, or `tls+tcp://` — never combined. This removes any plaintext-fallback path that could undermine an otherwise-encrypted deployment, and means RTU (a different, physical-access threat model) can never be used to bypass an active TLS-secured TCP configuration on the same instance. TLS itself is implemented via `rustls`, not hand-rolled — the project's "from scratch" philosophy applies to the Modbus protocol layer, not to cryptography.

**Identity: self-signed keys + fingerprint pinning instead of a CA hierarchy.** Both `client` and `server` generate their own self-signed keypair/certificate automatically on first run if none exists, persisted locally. Trust decisions are based **only** on the raw public-key fingerprint (full SHA-256) — other certificate fields (Subject, validity period, ...) are attacker-controlled since a peer signs its own cert, and are never consulted. This deliberately trades a CA's automatic verification for a human-verified pairing step, modeled on SSH host-key TOFU / HomeKit-style device pairing rather than PKI infrastructure. Alternatives seriously considered and rejected for the underlying encryption problem itself: a custom non-TLS scheme (a private function code doing an ephemeral ECDH handshake, then wrapping PDUs in an AEAD envelope) — rejected because designing a correct handshake/nonce/replay scheme from scratch is exactly the failure-prone territory TLS exists to avoid, and it would also need to keep the MBAP length field unencrypted for TCP framing and recompute RTU's CRC over ciphertext; and a pure TLS 1.3 PSK mode (no certs, `psk_dhe_ke` for forward secrecy) — still valid in principle, but doesn't give a technician per-client control over who connects, so it was superseded once that requirement surfaced.

**Server authentication (client trusts server):** the client is given the server's expected fingerprint once, out of band (e.g. read off a physical label at commissioning, passed as a CLI argument), and verifies every connection against it — protects against MITM / connecting to the wrong device.

**Client authentication (server trusts client) — mutual TLS with a fail-closed, filesystem-visible approval workflow:**
- The server also requires a client certificate (mTLS). Unknown/unapproved client fingerprints fail the TLS handshake outright (fail-closed) — the offered fingerprint is still observed and logged before the handshake is rejected, since the server sees the client's certificate before its own verification decides accept/reject.
- A new `client-trust/` FUSE subtree exists **only in the server's `InfusedFilesystem`** — threaded in via an `Option<Arc<Mutex<ClientTrustState>>>` constructor parameter, `None` on the client, so the directory simply doesn't exist there. This is the first FUSE feature in the project that is not symmetric between client and server.
  - `client-trust/connection_attempts/{approved,pending,rejected}.log` — three **fixed** log files, never one file per attempt/fingerprint (avoids unbounded inode growth from attacker-controlled input, the same class of problem H3 avoided by staying per-register instead of per-transaction-ID). Each is a bounded ring buffer logging every connection attempt (timestamp, outcome, fingerprint, source address).
  - `client-trust/approved/` — a **read-only** mirror of the currently approved fingerprint set. Deliberately not a write target, unlike every other write-capable directory in this project (`transactions/`) — see the approval channel below for why.
- **Approval/revocation channel:** a Unix domain socket (fixed path, mode `0600`, owned by the server's own service account), additionally verified via `SO_PEERCRED` on every connection (kernel-verified caller UID, independent of and in addition to the socket file's own permissions — defense in depth if the file permissions were ever misconfigured). A built-in `server admin approve|revoke|list <fingerprint>` subcommand wraps this so a technician never talks the raw protocol directly. Kept deliberately separate from the general FUSE mount: reading register data and granting a remote peer network access to the whole industrial system were judged different trust levels that shouldn't share one write mechanism, unlike `transactions/`, where "can write to the mount" is already the accepted trust boundary for register writes.
- Revoking a fingerprint must actively terminate any already-open connection using it, not just block future handshakes — a passive block alone would leave an already-connected revoked peer live until it disconnects on its own.
- Checking the current approved count against `--max-clients` and inserting a newly-approved fingerprint must happen inside one held lock (a single critical section covering read-count + insert + persist-to-disk), never as two separate lock acquisitions — otherwise concurrent approvals could race past the configured limit.

**Capacity limit:** `--max-clients N` (a connection/operational detail, supplied via CLI/config like other connection info, not the device-description TOML) bounds the number of **currently valid** approved fingerprints at once — revoking one frees the slot for a new approval. Separate concern from the DoS hardening below: this protects the size of the trusted-device roster, not the server's ability to withstand traffic floods.

**Persistence — the first durable state the server itself writes to disk.** Every other piece of runtime state in this project (`RegisterStore`, `PendingTransaction`, `WriteReport`) is deliberately in-memory only, lost on restart. Client-trust approvals are the first deliberate exception: losing every approval on every restart is a real availability problem, not just an inconvenience. The approved set is persisted to a flat file (e.g. `approved-clients.toml`, atomic write via temp-file-plus-rename, `0600`/service-account-owned — same discipline as the private key file) written by the server itself whenever the approval channel changes it. The file is read **once, at startup only** — never hot-reloaded or watched for external changes at runtime, so all live changes must go through the approval channel that owns writing it. This is what makes "compromising this file requires compromising the server's own account" actually true, rather than merely assumed.

**FUSE directory permissions — technician-configurable, except `client-trust/` which is hardcoded to maximum restriction.** A separate `fuse-permissions.toml` (a third config category alongside device-description TOML and connection CLI/config, governing local filesystem exposure policy) lets the technician set `mode`/`uid`/`gid` per top-level directory (`holding-registers`, `transactions`, `report`, `coils`). Enforced via the FUSE `default_permissions` mount option so the kernel checks against what `getattr` reports, rather than every trait method re-implementing checks by hand. `client-trust/` cannot appear in this file's schema at all — attempting to configure it is a hard parse error at startup, not a silently-ignored setting — and its `getattr` always reports `mode = 0o700`, uid/gid = the server process's own real UID/GID, regardless of configuration.

**DoS hardening for the TLS layer**, same "validate/bound untrusted input before spending resources on it" instinct as [[feedback-harden-server-against-malicious-peers]], applied one layer earlier than existing PDU-length checks:
- A timeout on the TLS handshake itself, independent of and in addition to the existing per-I/O-step `with_timeout` used for Modbus request/response.
- A global cap on concurrent in-flight connections/handshakes.
- A **per-fingerprint** concurrent-connection cap, so an already-approved but compromised or buggy client can't exhaust the connection pool by itself.
- Full protection against a distributed flood from many source addresses is explicitly out of scope for `infused_modbus` itself — that is upstream infrastructure's job (firewall/rate-limiter), not something the application layer can solve.

Implemented in the small-increment style "Working conventions" below describes — Milestones K through U each landed as their own commit(s) rather than one large one, see `git log` (`K1`..`U4` in each commit's own message) for the full sequence.

## Planned architecture

The project will be a **Cargo workspace** with (at least) these crates:

- **`protocol`** — the Modbus protocol implementation itself (TCP + RTU). This is a **from-scratch implementation**, not a wrapper around `tokio-modbus` — full control over protocol details was a deliberate choice.
- **`datafs`** (renamed from `fuse-fs` 2026-09-29, see "Pluggable data-representation layer" above) — the data-representation layer shared by client and server: the `holding-registers` and `transactions` directory logic, TOML device-description parsing, and the mapping between filesystem operations and Modbus reads/writes, for both the FUSE and `files` backends.
- **`sparkplug`** — a from-scratch Sparkplug B protocol implementation (protobuf wire format, `DataType`/`MetricValue`, `Metric`/`Payload` messages, topic namespace, session/sequence semantics). No dependency on `protocol`/`datafs` — the Modbus↔Sparkplug mapping is `client`-side glue, not part of this crate. See "MQTT (Sparkplug B) representation layer" below.
- **`client`** — binary crate; thin entry point wiring `protocol` (as Modbus master) + `datafs`/`sparkplug` together, configured via CLI args/config file for target device connection info.
- **`server`** — binary crate; thin entry point wiring `protocol` (as Modbus slave) + `datafs` together.

## Key technical decisions

- **Async runtime**: `tokio`, used across protocol I/O and FUSE update handling.
- **FUSE bindings**: `fuser` crate.
- **Modbus protocol**: implemented from scratch in the `protocol` crate (no `tokio-modbus` dependency).
- **Target platform**: Linux-only for now (FUSE is a Linux-specific dependency). Portability to other platforms (e.g. via WinFsp on Windows) is a desired future goal, not a current constraint — avoid over-engineering abstractions for it prematurely.
- **Device description vs. connection config**: kept deliberately separate — TOML describes *data shape*, CLI/config describes *how to connect*.

## Working conventions

- **Small, reviewable increments**: implement one method/function/struct (or similarly small unit) at a time, then stop for review before moving to the next one. Do not batch multiple units into one unreviewed change.
- **Extraction-Based Programming (Casey Muratori)**: write the concrete, specific solution first. Do not introduce an abstraction (generic function, trait, config-driven flexibility, etc.) speculatively — only extract one after the same concrete pattern has actually shown up and its real shape is known.
- **Testing**: most functions get regular unit tests. Interaction/integration-level behavior (e.g. protocol ⇄ FUSE interplay, transaction handling) is tested via a fuzzer that is itself part of this project — not an off-the-shelf fuzzing crate.
